# Agent Evaluation

## 简介

Agent 评估：衡量 Agent 在多步骤、有真实副作用的任务上表现的方法与基准。与传统模型基准（一问一答对分数）不同，Agent 评估要面对轨迹不唯一、结果多样、任务开放的难题，当前主流做法是"真实任务样本 + LLM-as-judge 比对基线"。

## 为什么重要

Agent 能不能上生产，最终由评估说了算——没有可复现的评估，改 prompt、换模型、调工具都是盲调。评估基准也是行业的"进度条"：如 ReviewBench 显示当前模型只能找回约 30% 的人工评审基线问题，说明代码评审 Agent 远未饱和，也量化了改进空间在哪。

## 核心概念

- **真实任务派生基准**：从生产数据（真实 PR 评审意见、真实工单）筛选出实质性样本构建任务，比合成任务更能反映实际水平（ReviewBench 的做法）。
- **覆盖率 vs 精确率**：Agent 评估的两个基本轴——找没找全（coverage）与报得准不准（precision），通常以 F1 为综合分；对评审类 Agent 尤其关键，误报直接消耗用户信任。
- **LLM-as-judge**：用模型比对 Agent 输出与人工基线是否命中同一问题（语义等价而非字面匹配），是开放式任务评分的主流方案，需注意 judge 本身的偏差。
- **策略是变量**：同一模型换评估目标明确的结构化 prompt，分数可显著提升——评估应把"模型 + 策略"作为整体对象，而非只测模型。
- **垂直领域基准由该领域头部厂商亲自构建**：Harvey LAB（法律，24 个执业领域、1,671 任务）延续了 ReviewBench（代码评审）的模式——由深耕该领域的公司自建全通过细则的真实任务基准，比第三方通用基准更贴近行业深水区的真实表现，这是专业服务型 Agent（法务/财务/医疗）评估的共同路径。
- **大规模真实科研任务作为压力测试**：ICML 2026 可复现性黑客松让 1,221 人用编码 Agent 复现 2,226 篇论文（占会议录用总量 34%）的核心主张，用自动化裁判模型统一判定"已验证/被证伪/仅玩具规模/无法判定"——是"真实任务派生基准"方法论在开放式科研复现场景的极限规模样本，量化基线为 51% 论文至少一条主张验证通过、23% 被证伪或存疑；结论强调最可靠结果来自人在回路，而非 Agent 完全自主判定。
- **专用裁判模型替代前沿模型做评估**：与其自建 LLM-as-judge，评估工具链厂商可以直接把"专门训练过的判断模型"做成托管服务——LangSmith Tuned Evaluators 首发的 Perceived Error 评估器，在标注对话数据上做专门后训练，判断准确度超过所有前沿模型，同时成本降低 82%（部分场景达 98%）；"垂直场景不需要前沿智能"这条效率哲学延伸到了评估工具本身。
- **基准"刷分"（benchmaxxing）检测**：模型在公开基准上高分不代表任务能力真的强，可能是学会了识别"自己身处哪个基准"进而复现基准特有模式；参考分歧、遮蔽实体恢复率、拼写惯例选择等探针可用来检测这种数据集指纹识别行为（ASR 领域的具体方法论，参见 [voice-agents](/topics/voice-agents)）。
- **结构化判定模型替代生成式 LLM-as-judge**：Jev 不生成文本判断，直接输出类型化判定结果——对同一组 500 条真实 Agent 决策的重复判定，与人工评审结果全部一致，连续型质量评分方差比主流 LLM judge 低 92～913 倍，成本与延迟低两个数量级；但结构化判定模型同样可能被 prompt injection 影响裁决，不是免疫的解法。
- **按系统终态而非自述评估 Agent**：最终回复与合法的工具调用都只是代理指标——Agent 可能话说得很对但写错了值、改错了记录或产生多余副作用；ThinkingBox 直接核查 Agent 在数据库里留下的终态与副作用，并对同一任务重复跑 20 次，把"能不能稳定做对"这个此前很少被单独测量的维度量化出来，是继核查"引用来源对不对"（ProvenanceGuard）之后，"不要只信 Agent 自己说了什么"这条方法论在"系统状态真实变化"这一核查对象上的延伸。
- **决策/判定正在独立成专门模型品类**：LangChain Jev（09-21）、OpenAI Decisions API（10-06，GPT-6 Luna 驱动）、LiquidAI d1（10-07，单次前向传播出确定性答案）三家不同背景的厂商在一个月内分别推出结构一致的解法——窄定义问题 + 类型化输出 + 远低于通用对话调用的成本/延迟；这意味着"分类/路由/决策下一步动作"这类任务不再默认走"调用通用 LLM 拿文本答案再解析"，评估/选型时应把专用决策模型当作与 LLM-as-judge 并列的独立选项考虑。
- **溯源正确性是独立于事实正确性的核查维度**：MCP Agent 拼接多个工具调用结果作答时，"论断是否被某处证据支持"（事实正确）与"论断引用的具体来源是否就是那个证据"（溯源正确）是两回事——"跨来源混淆"错误（论断为真但归错了源）会被只看事实支持度的传统核查方法放过，需要专门的溯源感知核查（详见 [mcp](/topics/mcp)）。
- **评估任务本身的构建方法论**：把"造题"拆成人工把关的 Spec 生成（Markdown 描述输入/环境/评分细则）与 Agent 自动执行的 Spec2Task 转换两阶段，让任务创建可并行、人工审核集中在成本最低的环节；跨任务共享的"world spec"（数据 schema、评分方法论、领域模式）进一步降低重复造题成本——是"真实任务派生基准"方法论在"怎么造题"这一工程环节的系统化。

## 最佳实践

- 评估集优先从自己的真实失败案例里建，通用基准分数与自己场景的相关性往往有限。
- 把 prompt/策略纳入被评估对象做 A/B，很多"模型不行"其实是策略不行。

### [2026-10-06](/today/2026-10-06)

OpenAI Decisions API 开放公测：GPT-6 Luna 驱动，专注开发者预定义问题与有限候选答案，比直接调用 Luna 快至多 10 倍，只按输入 token 计费（$0.10/百万，输出/缓存不计费）；与 LangChain Jev（09-21）、LiquidAI d1（10-07）共同构成"决策/判定独立成专门模型品类"的新趋势（详见 [openai-models](/topics/openai-models) ・ [model-efficiency](/topics/model-efficiency)）。

### [2026-10-03](/today/2026-10-03)

Microsoft × HuggingFace 发布 ThinkingBox：按 Agent 在数据库留下的终态与副作用评估，而非信任其最终回复或工具调用记录；507 个有状态企业工作流，18 个 LLM 上每个工作流重复跑 20 次，核心论点是"最终回复"与"合法的工具调用"都只是代理指标，只有留下的记录才能回答到底做对没有。

### [2026-09-29](/today/2026-09-29)

论文提出 ProvenanceGuard：针对 MCP Agent 的"溯源感知"事实核查方案——消费带稳定工具 ID/来源 ID/原始输出的 MCP 调用记录，把答案拆解成原子论断，逐条路由到对应来源证据核查支持度，再比对"声称的来源"与"实际路由到的来源"是否一致，输出逐条判定与整体放行/拦截结论；第一个把"引用对不对源"系统化为独立核查维度的方案（详见 [mcp](/topics/mcp)）。

### [2026-09-21](/today/2026-09-21)

LangChain 发布 Jev 并接入 LangSmith Evals：不生成文本的结构化判定模型，官方实测对 500 条真实 Agent 决策重复判定与人工评审全部一致，连续评分方差比 GPT-5.6 Luna/Terra 与 Claude Sonnet 4.6 低 92～913 倍，单次判定 0.44 秒、$0.00035，整组测试仅 $0.34（对比 Claude Sonnet 4.6 的 $28.17）。延续 08-18 LangSmith Tuned Evaluators"专用裁判模型替代前沿模型评估"的思路，但首次给出与人工基线完全吻合的大规模一致性数据；需警惕结构化判定同样可能被 prompt injection 影响裁决。

### [2026-08-25](/today/2026-08-25)

LangChain 分享 Agent 评估环境与任务的构建方法论：Spec 生成（人工把关）+ Spec2Task 转换（Agent 自动执行）两阶段流水线，"world spec"承载跨任务共享信息；已用于构建 GTM 调研、代码评审、trace 挖掘等内部基准。同日 LangSmith Engine 升级：IssueBench 得分翻倍以上，扫描 6000 多万条 trace 识别 2 万多个 issue（详见 [enterprise-ai-agents](/topics/enterprise-ai-agents)）。
