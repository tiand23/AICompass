# Inference Serving

## 简介

推理服务与部署：让训练好的模型在生产环境里高效、经济地跑起来的基础设施层——GPU 集群调度与利用率、serving 架构、推理降本、边缘部署。与 [model-efficiency](/topics/model-efficiency)（让单个模型本身更省资源，如量化/蒸馏/小型化）互补：这里关注的是"给定一批模型和一批硬件，如何调度、编排、分配才能把硬件利用率和产出价值最大化"。

## 为什么重要

Dharma AI 的研究指出：企业级 AI 集群普遍只有 30%-50% 的利用率，"利用率而非模型智能"正在成为生产环境规模化的主要瓶颈——两家 GPU 预算相当的公司，实际产出差距越来越取决于利用率而非集群规模。对正在自建或采购 GPU 算力的团队，这直接关系到能否把硬件投入转化为实际产出，而不是让大量算力闲置或被低效排队消耗。

## 核心概念

- **利用率 vs 智能**：GPU 的融资、折旧、电力成本按日历时间持续计提，与是否在跑有效负载无关；收入只在真正产出的计算时段产生——利用率不足是纯粹的成本浪费，与模型能力高低无关。
- **调度顺序独立于占用率影响产出价值**：同样的硬件占用率下，按优先级重排任务顺序仍可显著提升"加权产出价值"——利用率数字本身不能完整反映调度质量，需要同时看"占用了多少"和"占用的是不是该优先处理的任务"。
- **约束感知调度 vs FIFO**：FIFO 按到达顺序分配资源，对实时负载的峰值预留是静态、粗放的；约束感知调度器把实时需求建模成 24 小时尺度上的动态曲线，结合任务优先级动态重新分配批处理任务的位置——同一批任务、同一批硬件，仅调整调度逻辑就能大幅提升利用率与产出价值。
- **编排层 + 模型专精化，两者互补**：只做任务专精化（换更小的专用模型）而不做编排调度，省下来的算力没人去回收利用；只做编排调度而不做专精化，可回收的算力总量本身就有限——两条线需要同时推进。
- **持久化工作流作为编排原语**：把"资源协调"本身建模成持久化、可观测的工作流实体（如用 Temporal 的信号量 Workflow 做并发控制），比在应用代码里手写锁和重试计数器更可靠——这一模式同样适用于文档处理等非 Agent 场景（详见 [document-parsing](/topics/document-parsing)）。
- **围绕推理阶段特有瓶颈做定制硬件**：不把推理当均质算力负载对待，而是针对 prefill（预填充）与通信阶段的瓶颈专门做架构设计，最小化数据搬运延迟，是硬件层与调度层"把每一分算力都用在刀刃上"这一取向的另一种落地方式（OpenAI/Broadcom 的 Jalapeño 芯片是具体案例）。

## 最佳实践

- 优先审视调度顺序与资源预留策略，再考虑上更复杂的调度算法或采购更多硬件——很多利用率损失来自"预留但未充分复用"而非硬件不足。
- 按完整的 24 小时需求曲线做资源规划，而非按静态峰值预留；用较短周期（30-60 分钟）滚动重新优化以消化预测误差。
- 为不同工作负载类型（实时 vs 批处理、不同任务优先级）建专用的需求预测模型，而非套用通用预测器。
