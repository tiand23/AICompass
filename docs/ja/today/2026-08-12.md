## needle 2 が登場：スマホ/ウェアラブル/ロボット向けの 14MB 単一ファイル基盤モデル

- **概要**：cactus-compute/needle（1 日で +315、累計 4.6k スター、MIT ライセンス）——スマートフォン、ウェアラブル、スマートホーム機器、ロボットなどリソース制約の厳しい環境向けに設計された極小基盤モデル：モデル全体が単一の 14MB バイナリで、推論時のメモリ使用量は約 28MB（256 トークンのスライディングウィンドウ、ツール定義は KV シンクとして常駐）。アーキテクチャは通常のフィードフォワードネットワークを Hadamard MLP に置き換え、グループクエリアテンション（GQA）、ハッシュ化された n-gram テーブルによる Engram キーバリューメモリ、マルチレーンハイパーコネクション、サンドイッチゲーティング付き RMS 正規化を組み合わせ、Cactus Quants の CQ2-bit 量子化でこの体積まで圧縮している——設計は arXiv 論文（2607.18363）で公開。機能面では、ツール呼び出し（キャリブレーションされた信頼度スコアでゲーティングして実行）、大規模ツールカタログの検索（毎ターン上位 5 件をランキングして選択）、Pydantic モデルによるスキーマベースの構造化抽出、有効な JSON を保証する文法制約付きデコーディングに特化している。公式の主張：FunctionGemma 270M、LFM2.5 230M、Apple FM など同クラスの小型モデルより 5〜70 倍小さく（しかも f16 に対して 2-bit で）、ベンチマークでは互角に渡り合う。
- **なぜ重要か**：SLM/エッジモデル路線の体積軸における新たな最小記録だ——14MB の単一ファイルが 28MB の RAM で動くという規模感は、「腕時計やロボットに載る基盤モデル」を概念から実際にダウンロードして動かせるものへと変えた。パラメータ数以上に注目すべきはその機能上の焦点だ：汎用的な対話品質を追求するのではなく、ツール呼び出しと構造化抽出という Agent の最も中核的な 2 つの動作に特化し、信頼度ゲーティングと大規模ツールカタログ検索をネイティブに組み込んでいる。これは大型モデルを単純に縮小するのではなく、「リソース制約デバイス上の Agent」を独立した製品カテゴリとして設計する姿勢だ。

## LlamaIndex：LLM OCR のエラーは減っているのではなく、静かになっているだけだ

- **概要**：LlamaIndex は、LLM 駆動の OCR が従来型 OCR とは根本的に異なる壊れ方をすると論じる記事を公開した——Tesseract のようなエンジンは「肉眼で分かる壊れたゴミ」として失敗するが、LLM は流暢で一見もっともらしいテキストとして失敗し、欠落や誤りを覆い隠す。記事は 3 つの主流アーキテクチャ（ピクセルにアクセスしない OCR→LLM 訂正、VLM によるネイティブ転写、セグメンテーションベースの agentic オーケストレーション）を分解し、それぞれが独自の壊れ方をすることを示す。核心的なメカニズムは：視覚的証拠が曖昧な場合、モデルは「画像が最も裏付けるテキスト」よりも「テキストとして最もありそうなもの」を選好するというもの——口座番号や部品番号のような高エントロピーの文字列は特に脆弱で、言語の事前分布が最も弱い、まさにそこで最も必要とされているからだ。記事はまた、既存の指標が失敗すると指摘する：文字/単語誤り率はページ全体で平均を取るため、「文字精度 99%」と報告されたページでも、誤った 1% が合計金額や識別子であれば、そのページのデータは依然として無価値になりうる。結論：本番システムには、生のモデル単体では提供できないアーキテクチャレベルの制御——セグメンテーション、専用モデルへのルーティング、検証ループ、出力を元のピクセル位置にリンクする引用——が必要だ。
- **なぜ重要か**：文書解析という主軸に対する重要な方法論の補完だ——08-05 の「OCR はコモディティ化されない」記事と 08-11 の ExtractBench はそれぞれ「専用エンジンの方が強い」ことと「再現可能な横並び比較データ」を提示したが、この記事はより深いメカニズムの説明を補う：なぜ LLM OCR のエラーが特に危険なのか——エラーの数が多いからではなく、より偽装されていて、よりもっともらしく見えるからだ。「ページ平均の指標が重要フィールドのエラーを覆い隠す」という洞察は、CER/WER 系の指標で受け入れ検査を行っているどのチームにとってもすぐに使える方法論の修正だ——ページ全体の平均スコアだけを見るのではなく、フィールドタイプ（特に高エントロピーのフィールド）ごとに精度を測定すべきだ。
- **分類**：RAG

- **なぜ重要か**：この記事は、これまで散在していた Agent のコスト削減手段（モデルルーティング、プロンプトキャッシュ、評価駆動の効率改善、支出のハード上限）を、個別のテクニックの羅列としてではなく「3 段速度」という 1 つの統一されたガバナンスフレームワークに初めて組織化した——この階層化の発想自体が参考に値する：ランタイムレベルの最適化はほぼゼロコストだが効果は限定的、ワークフローレベルは継続的な投資が必要だがより大きな効果が見込め、ガバナンスレベルは効率の利得は生まないがリスクの露出に歯止めをかける——3 つは二者択一ではなく同時に走らせる必要がある。これは 08-11 の LangChain Switchyard モデルルーティング実測の、エンタープライズ側ガバナンス層への自然な延長でもある——「ルーティングをすべきか」という工学的判断を、より完全な組織レベルのコスト管理フレームワークの中に位置づけている。

## Liquid AI が LFM2.5-VL-3B を発表：エッジ向け視覚言語モデル、複数の能力で大型モデルに匹敵

- **概要**：Liquid AI が LFM2.5-VL-3B を発表した——LFM2.5 シリーズ初の視覚言語モデルで、SigLIP2 400M NaFlex 視覚エンコーダと 26 億パラメータのテキストバックボーンを組み合わせ、約 34 兆トークンで事前学習（前世代比 4 倍の視覚データ量）、分詞語彙を 12.8 万に拡張して非ラテン文字にも対応する。34 項目の評価タスク全体で平均正規化スコア 69.4% を達成：文書/OCR（DocVQA 91.1%、OCRBench v1 84.2%）、定位（RefCOCO 平均 87.9%）、UI 理解（ScreenSpot-v2 デスクトップ 78.7%／モバイル 81.2%／Web 82.2%）、複数画像（BLINK 61.5%）、ツール利用（ToolSandbox 59.5%）——いずれも同級の 3B モデルを上回り、一部の指標ではより大きな 4B 級モデルにも匹敵する。エッジ推論：M5 Max で 228 トークン/秒、Ryzen AI Max+ で 116 トークン/秒、メモリ使用量は約 3GB；Galaxy S26 Ultra では 20 トークン/秒；高並列時の GPU スループットは約 1.1 万トークン/秒で、同級の 4B モデルの約 2 倍。llama.cpp、MLX、vLLM、SGLang、ONNX に対応。
- **なぜ重要か**：LFM2.5 シリーズがテキスト単体（LFM2.5-2.6B）からマルチモーダルへと自然に拡張した事例だ——「ローカル Agent の推論主体」という役割を、テキストから画面/UI 理解、複数画像入力、視覚的定位にまで広げている。ScreenSpot 系とツール利用のスコアが特に重要なのは、それが「エッジ Agent はまず画面を理解してから操作する必要がある」という具体的なシナリオに直結しており、汎用的な画像 Q&A とは異なるからだ。体積をさらに圧縮しながら大型モデルに引けを取らない性能を維持していることは、本ナレッジベースが繰り返し確認してきた「効率化路線は能力を犠牲にする必要がない」という傾向をさらに補強する（詳細は [model-efficiency](/ja/topics/model-efficiency)）。
