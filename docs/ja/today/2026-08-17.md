## Google が Imagen 4 の 3 つの生成エンドポイントを正式終了、Gemini ネイティブ画像モデルへ全面移行

- **概要**：Google は 2026-08-17、Gemini API 側の Imagen 4 の 3 つの生成エンドポイント（`imagen-4.0-generate-001`、`imagen-4.0-fast-generate-001`、`imagen-4.0-ultra-generate-001`）を正式に終了し、呼び出し元に Gemini 3.1 Flash Image への移行を促した；Imagen 4 は既に 2026-03-24 に Vertex AI 側で非推奨化されており、今回は Gemini API 側での最終的な提供終了となる。Google は特に、これがシームレスな置き換えではないと明言している——従来の `generate_images()` メソッドは完全に消滅し、呼び出し元は単にモデル名を変更するのではなく、Gemini ネイティブの画像生成 API に合わせて呼び出し方法を書き直す必要がある。
- **なぜ重要か**：これは「独立した専用モデルラインが汎用の旗艦モデルに統合される」という収斂パターンの、また 1 つの事例だ——OpenAI が以前、独立ブラウザ製品 Atlas を ChatGPT/Codex に統合したのと同様に、Google は独立した画像生成モデルライン Imagen を Gemini のネイティブなマルチモーダル能力に統合しつつある。同じ収斂ロジックが、ベンダーや製品形態を問わず繰り返し現れている：独立した技術スタックと独立したブランドを維持し続けるよりも、能力を旗艦モデルの統一されたイテレーションサイクルに組み込む方を選ぶ、という判断だ。Imagen API を利用しているチームにとって、これは先送りできるモデルアップグレードではなく、明確な期限と破壊的な API 変更を伴う強制的な移行であり、事前の計画とテストが必要だ。
- **分類**：Models

## LlamaIndex が Temporal で文書処理オーケストレーションを再構築した詳細を公開：RabbitMQ から「永続ワークフロー」へ

- **概要**：LlamaIndex が、文書解析パイプラインの基盤スケジューリングを Temporal（ワークフローオーケストレーションエンジン）で再構築した経緯を公開した——それまでの RabbitMQ ベースの自前実装には、永続性・公平性・リソース調整のためのネイティブなプリミティブが欠けており、文書がますます複雑化する中（1 件で 1,200 ページ超、OCR + 視覚モデル + 複数回の処理が必要なものもある）、キューメッセージ・ロック・リトライカウンタでステータス追跡と公平性を継ぎ接ぎする方式に大量の技術的負債が蓄積していた。Temporal への移行後：ビジネスロジックは決定論的な Workflow（長期稼働するコーディネーター）と Activity（個別の作業単位）に分割される；並行性制御はリソースタイプごとの `SemaphoreWorkflow` インスタンスによるセマフォパターンを使用（呼び出し元は signal-with-start で許可を取得し `wait_condition` で待機し、read-then-write 型並行処理に付きまとう競合状態を回避する）；Temporal の中核機能である「永続的な関数実行」により、マシンの OOM によるジョブの静かな死が解消される——失敗したワークフローは手動のハートビート管理なしに最後のチェックポイントから自動的に再開する；そして専用の `concurrency-limiter` タスクキューと独自のワーカープールにより、許可取得の遅延が通常のアプリケーション処理を滞らせないようにしている。このシステムは現在 130 以上のファイル形式に対応し、Batch API を通じて日々数千万ページを処理している。
- **なぜ重要か**：これは、Deep Agents v0.7 や LangSmith Managed Deep Agents などの事例で既に繰り返し登場してきた「永続実行」というテーマが、文書処理という具体的で非 Agent 中心のシナリオに初めて着地した事例だ——「長時間タスクは失敗後に最初からやり直すのではなくチェックポイントから自動的に再開できる」という要件が Agent というカテゴリ固有のものではなく、あらゆる大規模非同期処理システムに共通する一般的な要件であることを示している。並行性制御を手書きのロックではなくセマフォ Workflow としてモデル化している点も注目に値する——「リソース調整」そのものを永続的で可観測なワークフローエンティティとして扱う方が、アプリケーションコード内にロックとカウンタを散らばらせるより信頼性が高く、インフラのプリミティブをオーケストレーション層へ押し上げるという、より広いエンジニアリングの潮流の具体的な一例だ。
- **分類**：RAG

- **出典**：https://www.llamaindex.ai/blog/temporal-scale-document-orchestration

## Dharma AI：同じ GPU クラスタでもスケジューリング順序を変えるだけで稼働率が 33 ポイント向上

- **概要**：Dharma AI が GPU クラスタ稼働率研究の第 2 弾を発表——8〜64 GPU の 7 つのベンチマークシナリオで、2 つのスケジューリング戦略を比較した：FIFO ベースライン（リアルタイム推論は固定の日次予約枠を保持し、バッチジョブは到着順にキューイングされる）vs 制約認識型アロケーター（リアルタイム需要を 24 時間スケールの動的な曲線として扱い、先着順ではなく優先度と時間的制約に基づいてバッチジョブの配置順序を並べ替える）。中心的な結果：訓練負荷の高いシナリオ（8 GPU、16 ジョブ）では、FIFO ベースラインの稼働率 53.6% に対し、制約認識型アロケーターは 87.0% を達成——33.4 ポイントの向上で、産出価値は 105.1% 増加に相当する；混合負荷シナリオでは稼働率が 20.8 ポイント向上、価値は 54.8% 増加；シナリオ全体の平均価値向上は約 52%。注目すべきは、最大規模のテスト（64 GPU、30 ジョブ）では両戦略とも稼働率が 44.9% で同じだったが、優先度で重み付けした産出価値はそれでも 15.9% 上昇した点だ——スケジューリング順序が、生の占有率の数字とは独立して産出品質に影響しうることを示している。結論：33 ポイントの回復は主に、リアルタイムピーク向けに不必要に予約されていた GPU を回収し、優先度を考慮した順序で再配分したことによるもの——著者らは、完全な 24 時間スケールで最適化すること、予測誤差を吸収するため 30〜60 分ごとに再最適化すること、汎用的な予測器ではなくワークロード固有の需要予測モデルを構築することを推奨している。
- **なぜ重要か**：この記事は「運用構造がアルゴリズムの精巧さに勝る」という主張に対して、めったにない、具体的なポイント単位での定量的な裏付けを与えている——33 ポイントの稼働率向上は、より賢いアルゴリズムやより強力なハードウェアからではなく、純粋に順序の入れ替えだけから生まれたものであり、複雑な自前スケジューラへの投資を検討中のチームに具体的な費用対効果の参照点を提供する。本ナレッジベースのマップでは長らく「推論とデプロイ」というニッチを「蓄積中」としてきたが、この記事はそこに体系的な定量データを初めて供給するものであり、そのニッチの出発点にふさわしい。
- **分類**：その他（推論とデプロイ）
