# 2026-10-07

## Claude Haiku 5.5 発表；Sonnet 5.5 のキャッシュ読み取り価格が再び低下；Managed Agents にデータ漏洩対策の URL 出典チェックを追加

- **概要**：Anthropic が Claude Haiku 5.5 を発表：100 万トークンのコンテキストウィンドウ、12.8 万の最大出力トークン、effort パラメータで駆動する適応的思考を備え、Claude API、Amazon Bedrock、AWS/Google Cloud 上の Claude Platform、Microsoft Foundry で同時提供。Haiku 4.5 からの移行に関する破壊的変更：拡張思考で手動の思考予算（`budget_tokens`）を指定すると 400 エラーが返る、適応的思考がデフォルトで有効になり応答が `thinking` ブロックから始まることがある、同じテキストがより多くのトークンとして数えられる。同日、Claude Sonnet 5.5 のプロンプトキャッシュ読み取り価格が 100 万トークンあたり $0.20 から $0.10 に低下（基礎入力価格の 0.05 倍、以前は 0.1 倍）；Python/TypeScript SDK にブラウザ使用ツールとコンピュータ使用ツールのベータ版ラッパークラスを追加（ツールループ、URL/ファイルポリシー、承認コールバックを自動処理）；Max/Team サブスクリプションに毎月の API クレジットが追加された。Claude Managed Agents は 3 つのネットワーク強化を一度に導入：`limited` ネットワークモードで `web_search`/`web_fetch` に `allowed_hosts` 許可リストを追加（範囲外は `url_not_allowed` エラー）；セッション作成時に `allowed_domains` が `allowed_hosts` の範囲外だと 400 エラーで拒否；そして `web_fetch` は現在「本セッション中に既に出現した」URL だけを取得できるようになった——Claude 自身の出力、システムプロンプト、添付文書、ツールの出力に含まれる URL はすべて拒否され（`url_not_in_prior_context` エラー）、取得可能な URL をユーザー自身のメッセージ本文に実際に出現したものに限定——データ漏洩リスクを直接の標的としている。
- **なぜ重要か**：Haiku 5.5 は、09-22/09-28 の Opus と Sonnet に続き、Claude の 3 つのモデル階層すべてが 1 か月以内に 5.5 世代への刷新を完了したことを意味する。`web_fetch` を「本セッション中に既に出現した URL のみ」に限定したことは、具体的で汎用性のあるデータ漏洩対策の設計パターンである——「この URL を取得できるか」という判断を「許可リストに入っているか」から「ユーザーが実際にこのアドレスに言及したか」へと一段厳しくし、prompt injection がツールの出力に悪意ある URL を仕込んで Agent にデータを外部送信させるという一般的な攻撃経路を直接断ち切っている。
- **分類**：Models
- **関連Topic**：[claude-models](/ja/topics/claude-models)・[agentic-safety](/ja/topics/agentic-safety)
- **出典**：https://platform.claude.com/docs/en/release-notes/overview

## LangChain が Managed Deep Agents v0.9（スケジュール/実行単位の設定/Slack リアクション）と Deep Agents の Skills 刷新を発表

- **概要**：LangSmith Managed Deep Agents v0.9 の公開ベータで追加された機能——Schedules SDK により、ユーザーはチャットでタスクのスケジュールを作成・変更・一覧表示・削除できる——繰り返しタスクは prompt と cron スケジュールを組み合わせ、一度限りのタスクは指定された時刻に実行され元のスレッドに結果を返す（例：「1 時間後にデプロイ状況を確認する」）；実行単位の設定により、同一のデプロイが実行時のコンテキストに応じて異なるモデル/指示/skills/接続ツール/サンドボックスを選べる（財務チャンネルでは請求関連の skill を使い、プラットフォームチームではインシデント対応ツールを使うなど、ほぼ同じ Agent をシナリオごとにコピー＆ペーストする必要がない）；Slack の確認リアクションも設定可能になった（デフォルトは 👀、無効化や別の絵文字への変更が可能）。同日、LangChain は《Revamping Skills in Deep Agents》を公開し、Skills の仕組みを刷新した：企業の skill ライブラリが数千件規模に成長したことで 3 つの問題が浮上した——ツールが skill とは別に開示されることで Agent が指示を読まずにツールだけを使ってしまう可能性があること、明示的にリクエストされた skill でもロードにもう 1 ラウンドのモデル呼び出しが必要なこと、長時間稼働するスレッドが再起動しないと新規/変更された skill を認識できないこと。3 つの具体的な変更——`include_tools` によって skill のメタデータにツールを紐づけられるようになり、ツールは Agent がその skill を読むまでコンテキストから隠され、読んだ時点で新しいシステムメッセージとして出現する（会話途中でのツール追加に対応するモデルでは、これによって prompt キャッシュを維持できる）；`pinned_skills` によってアプリケーションがモデル呼び出し前に指定した skill の完全な指示を会話に事前ロードでき、「発見してからロードする」という 1 ラウンドを省略できる；呼び出し時に `skills_metadata` を `None` に設定するとキャッシュされた skill リストが無効化され、長時間稼働するスレッドが最初からやり直さずに新規/変更された skill を認識できる——いずれもフレームワークの核心である「段階的開示」の原則を維持したまま実現されている。
- **なぜ重要か**：Managed Deep Agents v0.9 は 2 週間前の v0.8（新しい認証/記憶/チャネル）と 3 週間前の Connections に続くもので、ホスト型ランタイムの機能拡充のペースが明らかに加速している。Skills の刷新は、skill ライブラリが企業規模（数千件）に拡大した際に初めて、ツール開示と skill 開示の分離、長時間稼働スレッドが skill の更新を認識できないという、これまで見過ごされがちだった 2 つのエンジニアリング課題を体系的に解決したものであり、既に skill ライブラリを拡大したチームに直接役立つ。
- **分類**：Agent
- **関連Topic**：[deep-agents](/ja/topics/deep-agents)
- **出典**：https://www.langchain.com/blog/revamping-skills-in-deep-agents

## LlamaIndex が OpenDocRouter を発表：複数の文書解析モデルを統一する API

- **概要**：LlamaIndex が OpenDocRouter を発表——前沿モデル（Claude Opus 5.5、GPT-6 Luna、Gemini 3.8 Flash）とオープンソースモデル（MinerU2.5-Pro、TeleOCR、PaddleOCR-VL）を単一の API に統合し、文書を Markdown に変換する；1 つのエンドポイントで PDF/PNG/JPEG/URL の入力に対応し、最大 500 ページまたは 50MB まで処理できる；`layout: True` を設定すると、グラウンディングされたバウンディングボックスと読み順に沿ったレイアウト要素を持つ Markdown を出力し、モデルの素の能力に関わらず一貫したレイアウトクラスへ標準化される；同期（最大 50 ページ）と非同期の両方のリクエスト方式に対応；トークン単位の課金で、$25 クレジットから利用可能、モデル選択に応じて 1,000 ページあたり $0.86～$48.82。
- **なぜ重要か**：LlamaParse よりも軽量な代替として位置づけられている——より強力なパーサーモデルを自前で構築するのではなく、複数の文書モデルを管理する際の prompt 調整・レート制限・デプロイ・コスト最適化という手間を 1 つのルーティング層にまとめることで、開発者が最新モデル間を素早く切り替えて試せるようにし、実際に使った分だけを支払う形にしている——08-31 の Cohere Parse V5 が示した「コストは独立した選定軸である」という流れをさらに製品化したもの。
- **分類**：RAG
- **関連Topic**：[document-parsing](/ja/topics/document-parsing)
- **出典**：https://www.llamaindex.ai/blog/introducing-opendocrouter

## LiquidAI が d1-3B / d1-omni-600M をオープンソース化：単一の順伝播で確定的な答えを出すエッジ向け決定モデル

- **概要**：LiquidAI が決定モデルファミリー d1 のオープンウェイト版を公開——d1-3B と、実験的な多モーダル版 d1-omni-600M（テキスト＋画像、テキスト＋音声の両方に対応）；通常の生成系 Transformer が逐次トークンを生成するのとは異なり、d1 系列は単一の順伝播で確定的な答えを直接返す；d1-3B は平均スコア 82.9 で Decider 4B のベースラインを上回り、d1-omni-600M はパラメータ数が 4 分の 1 でありながら Decider 2B を上回る 78.4 を記録；デスクトップ GPU 上では単一クエリを 10 ミリ秒未満、384 ピクセルの画像を 18 ミリ秒未満で処理し、NVIDIA Jetson などのエッジデバイスでは 50 ミリ秒未満で応答する；重みは Hugging Face で公開されローカルダウンロード可能。
- **なぜ重要か**：同時期の OpenAI Decisions API や、それ以前の LangChain Jev と合わせて、「意思決定/判定タスクが独立した専用モデル品類へ分化する」という流れのエッジ向けの事例である——テキスト生成そのものを行わず単一の順伝播で確定的な答えを出すという設計は、この流れの中でも最も先鋭化したアーキテクチャの選択である（詳細は [model-efficiency](/ja/topics/model-efficiency) ・ [agent-evaluation](/ja/topics/agent-evaluation)）。
- **分類**：Models
- **関連Topic**：[model-efficiency](/ja/topics/model-efficiency)・[agent-evaluation](/ja/topics/agent-evaluation)
- **出典**：https://www.liquid.ai/blog/d1-open
