## コミュニティが 817 件のサイバーセキュリティ Skill を公開：6 大セキュリティフレームワークにマッピング、Claude Code など 20+ プラットフォームに対応

- **概要**：mukul975/Anthropic-Cybersecurity-Skills（1 日で +198、累計 2.85 万スター）——コミュニティが維持するサイバーセキュリティ skill ライブラリで、817 件の構造化スキルは（汎用チュートリアルやスクリプトではなく）実際の実務者ワークフローに由来する。29 のセキュリティ領域をカバー（クラウドセキュリティ 66 件、脅威ハンティング 58 件、脅威インテリジェンス 52 件、ネットワークセキュリティ 43 件、Web アプリケーションセキュリティ 42 件、デジタルフォレンジック 41 件、マルウェア解析 39 件、ID/アクセス管理 37 件など、コンプライアンスやハードウェアファームウェアセキュリティにまで及ぶ）。各 skill は統一された構造——YAML frontmatter（Agent が高速に発見できるように）+ Markdown の段階的ワークフロー + 参考資料 + 補助スクリプト + テンプレート資産——を採用し、6 つの業界フレームワークにマッピングされる：MITRE ATT&CK v19.1（805 件が 15 の戦術・290 の技術にマッピング）、NIST CSF 2.0（804 件が全 6 機能をカバー）、MITRE ATLAS 2026.07（93 件、AI/ML への敵対的脅威と Agentic AI 攻撃ベクトルに特化）、MITRE D3FEND v1.4.0（139 件の防御対策）、NIST AI RMF 1.0（97 件、ガバナンス機能と GenAI リスクカテゴリ向け）、MITRE F3 不正対策フレームワーク（94 件、サイバー経由の金融詐欺対策）。token コストを抑えるため段階的開示を採用：frontmatter だけのスキャンは 1 件あたり約 30 token（Agent は 817 件全体を一度にスキャンできる）、完全な内容（500〜2,000 token）は候補が一致した場合にのみロードされる。Claude Code、GitHub Copilot、Cursor、Gemini CLI、OpenAI Codex CLI など、agentskills.io 標準に準拠する 20 以上のプラットフォームにネイティブ対応。Apache 2.0 ライセンス。
- **なぜ重要か**：サイバーセキュリティという高度に専門的な垂直領域で、単一の MITRE ATT&CK だけでなく 6 つの業界標準フレームワークに体系的にマッピングされた、これほどの規模のオープンソース skill 集合が登場したのはこれが初めてだ。サイバーセキュリティ実務者の暗黙知（脅威ハンティングを実際にどう行うか、デジタルフォレンジックの手順は何か）を、Agent が直接読み込んで実行できる知識レイヤーに構造化している。本ナレッジベースがこれまで記録してきたシグナル——OpenAI の Daybreak（サイバーセキュリティモデルへの段階的アクセス）や reverse-skill（ペネトレーションテスト skill ルーターパック）——と併せて見ると、「サイバーセキュリティの Agent 化」はモデル層（専用モデル）、ツール層（ペネトレーションテストツール）に続き、いまや知識層（構造化 skill ライブラリ）にまで全面的に広がりつつある。「frontmatter の軽量スキャン + 一致時のみロード」という段階的開示の設計も、大規模 skill ライブラリのコンテキストコストを抑える再利用可能で具体的なパターンだ。

## ai-memory がオープンソース化：コーディング Agent の長期記憶レイヤー、ベンダーを跨いだシームレスな引き継ぎに対応

- **概要**：akitaonrails/ai-memory（1 日で +207、累計約 2.1k スター、MIT ライセンス）——コーディング Agent CLI 向けの長期記憶システムで、「Claude Code をタスクの途中で終了し、同じディレクトリで OpenAI Codex を起動して、アーキテクチャを再度説明することなく作業を続ける」というシナリオを中心に設計されている。生の会話ログを保存する代わりに、セッションのライフサイクルイベント（prompt、ツール呼び出し、失敗）を脱敏し、検索可能な Markdown wiki に編纂する；セッション終了時には未解決の課題と次のステップを含む引き継ぎサマリーを生成し、次の Agent は最初の prompt を受け取る前に「どこまで進んでいたか」のブリーフィングとしてこれを受け取る。アーキテクチャとしては、単一の Rust バイナリが 1 つのデータディレクトリを管理する（git バージョン管理された wiki をソースオブトゥルースとし、脱敏済みで不変の生転記、SQLite+FTS5 データベース、ローカル埋め込みモデル、ローリングログ）；ライフサイクルフックはイベントを「発火して忘れる」形でローカルの HTTP サーバーに送信し、サーバーは SQLite への書き込みをシリアライズし、セッションページを編纂し、FTS5 全文検索・エンティティマッチ RRF・任意のベクトル検索で検索を提供する。すでに Claude Code、Codex、Command Code、Devin、OpenCode、Cursor、Kiro CLI 向けのフック実装を備えており——各 Agent のフックスキーマは異なるが、いずれも同じサーバーに観測データを POST する。これがベンダーを跨いだ引き継ぎを実現する鍵だ。また MCP サーバー（`memory_query`/`memory_write_page`/`memory_feedback` などのツール）、読み取り専用の Web UI、モデル呼び出しに一切依存しない「ゼロ LLM モード」（FTS5 + 宣言的エンティティ + ルールベースの要約にフォールバック）も提供する。
- **なぜ重要か**：これまでの記憶インフラの議論は主に「同じ Agent/同じベンダー内でどう覚え続けるか」に焦点を当ててきた——ai-memory はその範囲を「別のベンダーの Agent に切り替えても記憶を持ち運べるか」へと広げている。複数のコーディング Agent ツールを併用するのが常態化した今（以前 holaOS も同じ傾向を示していた）、これは自然だがこれまであまり作られてこなかった次の一歩だ：記憶そのものが単一ベンダーの harness にロックされているべきではない。「ゼロ LLM モード」という設計選択も注目に値する——基本的な検索・要約能力がモデル呼び出しに一切依存しないため、「記憶システムを持つこと」と「大型モデルを使う余裕があること」を切り離しており、採用のハードルを下げる実用的な発想だ。
- **分類**：Agent
- **関連 Topic**：[agent-memory](/ja/topics/agent-memory) ・ [coding-agents](/ja/topics/coding-agents)
- **出典**：https://github.com/akitaonrails/AI-Memory

## IBM Research のフォローアップ研究：Agent 記憶は「多いほど良い」わけではなく、モデル階層ごとに「投与量を較正」すべき

- **概要**：IBM Research が ALTK-Evolve（08-11 に収録した記憶蒸留フレームワーク）のフォローアップ研究を発表。「規模の異なるモデルは実際どれだけの記憶を必要とするか」を専門的に検証し、その中核的な発見は「記憶は多いほど良い」という直感を覆すものだった。研究は 8 個のモデル（117B〜745B パラメータ）を AppWorld（シミュレートされたアプリを跨ぐ 585 の多段階タスク）で評価し、タスク目標達成率（TGC）とシナリオ目標達成率（SGC、タスクのバリエーションを跨いだ全通過信頼性）の 2 指標で測定、3 つの異なるパターンを示した：**余力のある強いモデル**は完全なガイドライン注入から恩恵を受ける——DeepSeek-V3.2 は全量ガイドラインでタスク完了率が 9.5 ポイント向上；**より弱い/小さいモデル**はむしろ精選検索（高支持度のガイドラインの小さなコア + タスク関連の選択）の方が成績が良い——gpt-oss-120b は精選検索でベースラインから 16.1 ポイント向上し、token 消費は 5% 増に留まった；**既に飽和したモデル**はどちらの投与でも一切向上しなかった——GLM-5 はどちらの投与方式でも改善幅が 0.0 ポイントで、能力の天井またはガイドライン関連性のボトルネックの存在を示唆する。コスト面では、精選検索はごくわずかな token 追加でより高い精度を得られる一方、完全注入は 51%〜78% の token コスト増をもたらす（信頼できる prompt キャッシュ戦略で本番コストを部分的に相殺できる）。
- **なぜ重要か**：この研究は「Agent 記憶の最適化」を「積み上げる」から「階層ごとに較正する」へと再定義する——どれだけの記憶を与えるべきかはモデルの階層次第であり、情報量の最大化を単純に追求することではない。これは 08-11 の ALTK-Evolve の知見（「選択的投入は token を節約しつつ精度を落とさない」）に対する重要な補足・深化であり——前回は「精選検索」という経路自体が有効であることを証明したが、今回は「精選検索が有効であること」自体が普遍的真理ではなく、モデル階層によって異なる現象であることを明らかにした——強いモデルが必要とするのは「十分な情報量」、弱いモデルが必要とするのは「十分に精密な情報量」であり、飽和したモデルには何を与えても意味がない。記憶システムを設計しているチームにとって、これは「単一の記憶投入戦略で万能」という前提自体が誤りである可能性を意味し、対象モデルの能力階層ごとに別々にチューニングする必要がある。
- **分類**：Agent
- **関連 Topic**：[agent-memory](/ja/topics/agent-memory)
- **出典**：https://huggingface.co/blog/ibm-research/altk-evolve-hmm

## Sentence Transformers v6.0 がマルチベクトル（後期相互作用）Embedding をネイティブサポート：ColBERT 式検索が主流ライブラリへ

- **概要**：Sentence Transformers v6.0 が `MultiVectorEncoder` を追加し、ColBERT 式のマルチベクトル（後期相互作用、late-interaction）Embedding モデルをネイティブサポートする——文書全体を 1 つのベクトルに圧縮する稠密 Embedding とは異なり、マルチベクトルモデルは各 token に 1 つのベクトルを保持する（9 token の文書は 1×128 の単一ベクトルではなく 9×128 の行列になる）。「相互作用」をスコアリング段階まで遅らせることで、バイエンコーダのオフラインインデックス能力とクロスエンコーダ的な精密なクエリ・文書比較を両立する。スコアリングには MaxSim 演算子を用いる：各クエリ token について文書内の全 token の中から類似度最大の 1 つを見つけて合計する——「各クエリ語が文書内でそれを最もよく説明する語を指し示す」ソフトなアラインメントであり、文字が一切重ならないが意味的に関連する（類似度 0.94）"live" と "inhabit" のようなマッチも捉えつつ、完全一致も失わない。新ライブラリは任意の PyLate および Stanford-NLP の ColBERT チェックポイント、さらに視覚文書モデル ColPali にネイティブ対応し、テキスト/画像/音声/動画のマルチモーダルをカバーする非対称の `encode_query()`/`encode_document()` インターフェースを提供する。ベンチマークデータ：同規模モデルの比較では、NanoBEIR 上でマルチベクトル版（LateOn、平均 NDCG@10 0.6868）が 13 データセット中 9 つで対応する稠密版（DenseOn、0.6764）を上回った；しかしストレージコストははるかに高い——Natural Questions の 4,874 パッセージをエンコードする場合、稠密（MiniLM）は 7.5MB で済むが、マルチベクトル（128 次元）は生データで 311.5MB（PLAID インデックス圧縮後は約 92MB）を要する；token プーリング（pool_factor=2）はベクトル数を半減させつつ精度低下を 1% 未満に抑えられる。Qdrant/Weaviate/Vespa/LightOn fast-plaid などのネイティブインデックスが既に対応済みで、fast-plaid は 4,874 文書で PLAID インデックスに近い約 11ms のクエリレイテンシを実現する。
- **なぜ重要か**：これは「検索精度 vs ストレージコスト」というトレードオフ曲線上で、これまでニッチだった技術路線（ColBERT 式マルチベクトル検索）が主流ライブラリに正式に取り込まれた初めての事例だ——これまでマルチベクトル検索は主に論文と専門ライブラリ（PyLate など）に留まっていたが、Sentence Transformers のネイティブサポートは、これが本番級 RAG/検索スタック選定における通常の選択肢の一つになり、自分で組み立てる必要のある実験的手法ではなくなったことを意味する。13 データセット中 9 つで同規模の稠密モデルを上回ったという結果は、長く引用されながら統一的な実装検証を欠いていた「稠密ベクトルは圧縮で情報を失う」という主張に、再現可能な対照データを与える；ストレージコストが桁違いに高いという点も、これが無償のフリーランチではないことを示しており、自分のリコール要件とストレージ予算に応じてトレードオフを判断すべきで、デフォルトで切り替えるべきものではない。
- **分類**：RAG
- **関連 Topic**：[vector-databases](/ja/topics/vector-databases) ・ [rag](/ja/topics/rag)
- **出典**：https://huggingface.co/blog/multi-vector-encoder

## LangSmith が「調整済み評価器」を発表：専用の小型モデルがフロンティアモデルより正確に Agent を判定し、コストを 82% 削減

- **概要**：LangSmith が Tuned Evaluators（調整済み評価器）を発表——マネージド評価サービスで、「本番環境の trace に有用なシグナルを自動的に付与する」ことを「チームが自前で評価器を構築する」から「取り付けるだけで使える」に変える：LangChain が事前学習済みでバージョン管理された裁判モデルをエンドツーエンドで維持し、prompt エンジニアリング、モデル選定、認証情報管理、インフラをすべて引き受けるため、チームはトレーシングプロジェクトに取り付けるだけでよい。最初に公開された評価器は Perceived Error（知覚エラー検知）——「Agent がミスをした、リクエストを誤解した、あるいは対話を意図しない方向に導いた」会話を識別するもので、明示的シグナル（ユーザーの訂正、拒否）と暗黙的な推論（自己矛盾する返答、ミスの認め、未解決の結果）の両方を根拠とする。このモデルはラベル付けされた対話型 Agent trace で事後学習を行うことで専用能力を獲得し、実測で「すべてのフロンティアモデルを上回る」判定精度を示しつつ、コストを 82% 削減——会話の構成によっては一部の顧客ワークロードで削減幅が最大 98% に達する。利用条件：スレッドは少なくとも 2 往復の人間-AI メッセージペアとアイドル期間の設定を満たす必要があり、条件を満たしてから 12 時間以内に評価が完了する；現時点では Plus および Cloud Enterprise の米国リージョンでのみ利用可能；課金は成功した実行に対してのみ発生し、スキップまたは失敗した評価は無料。
- **なぜ重要か**：これは「専用の小型モデルでフロンティアモデルに代えて LLM-as-judge を行う」というコスト削減の発想が、評価という具体的な場面で製品化された事例だ——これまでこの発想は研究成果や自前構築のソリューションとして現れることが多かった（08-11 のモデルルーティングの実測結果など）が、今回は評価ツールチェーンのベンダー自身がすぐに使えるマネージドサービスに仕立てており、ユーザーは自分で判定モデルを学習・維持する必要がない。「フロンティアモデルより正確で、しかも安い」という結果自体も注目に値する——専用の事後学習モデルが狭いタスク（会話が誤った方向に進んだかどうかの識別）で汎用フロンティアモデルの判断力を上回ることは、「垂直的な場面にフロンティア級の知能は不要」という効率哲学が評価領域にも及んでいることを示す実証例だ；これはまた、本ナレッジベースで繰り返し登場する「垂直ベンチマークはその領域の当事者自身が構築する」というパターンの延長でもあり——今回は評価ベンチマークではなく評価ツール自体が専用化された。
- **分類**：Agent
- **関連 Topic**：[agent-evaluation](/ja/topics/agent-evaluation)
- **出典**：https://www.langchain.com/blog/introducing-langsmith-tuned-evaluators-starting-with-perceived-error
