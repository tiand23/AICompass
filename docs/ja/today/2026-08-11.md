## LlamaIndex が ExtractBench を発表：370 件の実企業文書、14 の抽出システムを横並び評価

- **概要**：LlamaIndex は ExtractBench を発表した——370 件の実企業文書を対象に 14 の抽出システムをテストするオープンなベンチマークで、完全性（completeness）、根拠性（grounding、抽出結果を文書内の原位置まで追跡できるか）、ページあたりコストの 3 軸でスコアリングする。
- **なぜ重要か**：これは 1 週間前の「文書 OCR は前沿モデルにコモディティ化されない」（2026-08-05）という立場記事の自然な続編だ——前回は論証、今回は再現可能な横並び比較データを提示し、「専用パーサー vs 汎用大型モデル」という選定論争を「我々はこう考える」から「実測結果はこうだ」へと変えた。3 つの評価軸も注目に値する：completeness と grounding はそれぞれこれまで繰り返し強調されてきた「抽出漏れを防ぐ」と「空間的位置特定/証拠チェーン」に対応し、コスト軸は選定を工学的現実に引き戻す——精度は高ければ高いほど良いのではなく、精度とページあたりコストのコストパフォーマンス曲線こそが問題になる。ベンチマークは LlamaIndex 自身が構築したもので立場はこれまでと変わらないが、公開・再現可能な評価手法論そのものは業界への正味の貢献である。
- **分類**：RAG
- **関連 Topic**：[document-parsing](/ja/topics/document-parsing)
- **出典**：https://www.llamaindex.ai/blog/introducing-extractbench

## Claude Compliance API にローカルセッション記録の取得機能を追加：Cowork / Claude Code が全工程監査可能に

- **概要**：Claude Enterprise の Compliance API に 3 つの新しいエンドポイント（`GET /v1/compliance/apps/sessions/local` と、セッション詳細・メッセージ転記を取得するエンドポイント）が追加され、ユーザー自身のマシン上で動作する Cowork および Claude Code セッションの完全な記録と転記テキストを取得できるようになった。現在 beta 段階で、既存の Compliance Access Key と `read:compliance_user_data` スコープが必要。
- **なぜ重要か**：これまで企業側の推論層監査は主に Inference Hooks（2026-08-05 導入）——リクエストがモデルに届く前に allow/deny を裁定する仕組み——に頼っていたが、従業員の PC 上でローカルに動く Agent セッションの中で実際に何が起きたかについては、企業側の可視性が欠けていた。今回 Compliance API がローカルセッションの完全な転記も検索可能な範囲に含めたことで、「事前ブロック」だけではカバーしきれない「事後監査」の半分が埋まった。両者を合わせると、企業側のローカル実行 Agent に対する可観測性は「ブロックできるか」から「何が起きたかすべて確認できるか」まで拡張されたことになり、Agent ガバナンスツールチェーンのエンタープライズ・コンプライアンス軸をさらに補強するものだ。
- **分類**：その他（安全）
- **関連 Topic**：[agentic-safety](/ja/topics/agentic-safety) ・ [claude-models](/ja/topics/claude-models)
- **出典**：https://platform.claude.com/docs/en/release-notes/overview

## LangChain が NVIDIA Switchyard で実測：Agent の呼び出しのうち前沿モデルが本当に必要なのはわずか 7%

- **概要**：LangChain は自社の Deep Agents 評価セット（145 件のマルチステップタスク、1 タスクあたり平均 6.3 回の呼び出し、カスタマーサポート・障害調査・ワークフロー自動化をカバー）を、オープンソースのモデルルーティングライブラリ NVIDIA NeMo Switchyard に通し、「エスカレーションモード」で Nemotron 3.5 Lightning（30B）と Claude Opus 4.8 の間をルーティングした。結果：93% の呼び出しが安価な Nemotron にルーティングされ、消費した費用はわずか総額の 10.4%；Opus にエスカレートしたのはわずか 7% だったが、費用の 68.4% を消費した。ルーティング全体では 80% の精度を 1 回の実行あたり $3.00（完了タスクあたり $0.026）で達成し、Opus 単独実行の 86% 精度・$11.45（タスクあたり $0.092）と比べてコストを 74% 削減、精度の低下はわずか 6 ポイント。Nemotron 単独実行では精度 77.7%、$0.72 だった。記事はルーティングが割に合うかどうかを判断する式も提示する：判断モデル（judge）のコスト ÷（高価なモデルのコスト − 安価なモデルのコスト）＜ 安価なモデルにオフロードされる作業の割合——判断モデル自体の費用がルーティング総費用の 21.2% を占めており、2 つのモデルの価格が近いほどルーティングは割に合わなくなる。
- **なぜ重要か**：「Agent の呼び出しの大半は前沿モデルを必要としない」という直感に、初めて公式かつ再現可能な定量データの裏付けが与えられた——「単純なタスクには SLM を使え」という漠然とした一般論にとどまらず、93%/7% という具体的な呼び出し分布、74% というコスト削減幅、そして「判断モデルのコスト vs 価格差」という実行可能な意思決定の公式によって、「モデルルーティングをすべきか」が経験則ではなく事前に計算できるエンジニアリング判断に変わった。複数モデル構成の Agent アーキテクチャを設計中のチームにとって、そのまま流用できるコスト-精度のトレードオフフレームワークだ。
- **分類**：Agent
- **関連 Topic**：[model-efficiency](/ja/topics/model-efficiency) ・ [deep-agents](/ja/topics/deep-agents)
- **出典**：https://www.langchain.com/blog/switchyard-agent-routing-benchmark

## LangChain：Agent に本当に必要なのはツールの数ではなく「自分専用のコンピュータ」——monday.com Sidekick の事例

- **概要**：LangChain は、Agent の能力の上限を決めるのは事前に組み込まれたツールの数ではなく、永続的で隔離された、コードを実行できる環境を持っているかどうかだと主張する。記事は monday.com の Sidekick がかつて単一の Agent に 200 以上の事前定義ツールを詰め込み、無関係なツール定義でコンテキストが汚染され、モデルの判断力が低下し、コストが上昇していたにもかかわらず、根本的な問題は解決されなかったことを明かす。LangSmith Sandboxes（ハードウェアレベルで仮想化された microVM。カーネルを共有するコンテナではない）に切り替えたことで、Sidekick は独自のファイルシステム、shell、パッケージマネージャー、ネットワークアクセス、セッションを跨ぐ永続状態を獲得し、あらかじめ用意されたツールリストに縛られる代わりに、自らコードを書いて実行し、結果を確認し、動的に適応できるようになった。記事はコンテナレベルの隔離が抱える現実のリスクも指摘する：2025 年 9 月の Shai-Hulud npm ワームは preinstall スクリプト経由で 500 以上のパッケージを汚染し、CVE-2026-31431（732 バイトの Python スクリプトで主要な Linux ディストリビューションを軒並み root 化できる）は、カーネルを共有するコンテナが「信頼できない、モデルが生成したコード」を実行する Agent の隔離には不十分であることを示している。
- **なぜ重要か**：これは「Agent にツールを積み増す」という路線の限界を示す具体的な反証事例だ——200 以上のツールはむしろ Agent を鈍くし高コストにした。導き出されるアーキテクチャ上の結論は、能力は「自分でツールを見つけ、実行し、結果を見て、適応できる」計算環境から生まれるのであって、網羅的に事前定義されたツールカタログからではないということだ。これは「ストレージ層」と「実行バックエンド」を切り離した Cloudflare computer（2026-08-06）の発想とも呼応するが、今回は明確な失敗事例のデータポイント（200 以上のツールによるコンテキスト汚染）と明確なセキュリティ上の動機（コンテナ隔離ではモデル生成コードのサプライチェーンリスクを防ぐには不十分）が加わり、「Agent には本物のコンピュータが必要だ」という主張がアーキテクチャ上の直感から、実際の障害事例に裏付けられたエンジニアリング上の結論へと変わった。
- **分類**：Agent
- **関連 Topic**：[agent-sandboxes](/ja/topics/agent-sandboxes) ・ [deep-agents](/ja/topics/deep-agents)
- **出典**：https://www.langchain.com/blog/give-your-ai-agent-its-own-computer

## IBM が ALTK-Evolve をオープンソース化：「選択的投入」で Agent 記憶の token コストを 60% 削減

- **概要**：IBM Research が、Agent Lifecycle Toolkit の記憶コンポーネントである ALTK-Evolve を発表した。Sambanova の ACE（Agentic Context Engineering）と根本的な発想は同じ——どちらも実行トレースから「教訓」を抽出し、支持回数（そのルールを裏付けた独立エピソードの数）で追跡しながら再利用可能なガイドラインに統合し、どちらも「圧縮」を拒否する——概括的な指示に要約するのではなく、逐条の詳細を保持する（要約は情報を失う）。決定的な違いは投入方法にある：ACE は毎ステップ完全な playbook をまるごと注入するのに対し、ALTK-Evolve は投入を設定可能にしている——支持度の高いガイドラインの小さな固定コアを土台にしつつ、タスクごとに関連する数件を追加で選んで拡張する。AppWorld ベンチマークでは、DeepSeek-V3.2 が 168 タスクを実行：ALTK-Evolve はタスク目標達成率 89.3%・1 タスクあたり 26.3 万トークンを記録し、ACE は 80.4%・63.4 万トークン——ALTK-Evolve は ACE の約 40% の token コストでより高い精度を達成した。より弱いモデルである gpt-oss-120b では精度はほぼ互角だったが、ALTK-Evolve が使った token は ACE の約 7 分の 1（11.6 万 vs 77.7 万）だった。難易度別に見ると、ALTK-Evolve の優位性は難しいタスクほど顕著になる（gpt-oss-120b の困難タスクで 31.8% vs ACE の 23.8%）——これは「正しい教訓を選び取ること」が「すべての教訓を利用可能にしておくこと」より重要であることを示しており、モデルの能力が弱く、長すぎるコンテキストが判断力を圧倒しやすい場合に特に当てはまる。
- **なぜ重要か**：これは Agent の記憶／コンテキストエンジニアリング領域における具体的な方法論の改良だ——ACE が示した「圧縮せず、逐条でカウントして経験を保持する」という発想はすでに 1 つの前進だったが、「毎ステップ全量注入する」やり方は依然として大きな token コストを伴っていた。ALTK-Evolve は「保存は全量の詳細を保つが、投入は選択的に行う」ことで両方を実現できることを示した——ACE が圧縮を拒否することで得た精度上の利益を失うことなく、token コストをさらに 60〜85% 削減できる。Agent 向けの長期記憶／経験再利用システムを構築しているチームにとって、これは具体的で実行可能な最適化の方向性を示す：記憶の保存はきめ細かい粒度を保ちつつ、検索・投入の段階では「覚えていることを全部送る」のではなく選択的な想起を行うべきだということだ。
- **分類**：Agent
- **関連 Topic**：[agent-memory](/ja/topics/agent-memory) ・ [model-efficiency](/ja/topics/model-efficiency)
- **出典**：https://huggingface.co/blog/ibm-research/altk-evolve-sldd
