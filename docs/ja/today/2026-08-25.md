## OpenAI と Broadcom が推論チップ Jalapeño の初回実測結果を発表：スループット・レイテンシとも NVIDIA Blackwell を上回る

- **概要**：OpenAI と Broadcom（2025-10 に提携を発表）が共同開発したカスタム推論チップ Jalapeño の初回ベンチマーク結果が公開された。このチップは推論フェーズ専用に設計されている——prefill（プレフィル）と通信フェーズのボトルネックを中心にアーキテクチャを最適化し、データ移動と通信遅延を最小化する。モデル状態（生成中に使う KV キャッシュを含む）は明示的にローカルへ配置・保持できる。SemiAnalysis の InferenceX ベンチマークで GPT-OSS 120B、DeepSeek R1 670B、Kimi K2.5 1T の 3 モデルをテストしたところ、NVIDIA Blackwell システム（GB200/GB300）と比べてワットあたりのピーク性能が 1.5〜1.9 倍、エンドツーエンドのレイテンシが 1.7〜3.6 倍低減；高インタラクティブなワークロードでは性能向上が 2.1〜4.1 倍に達した。OpenAI は 2026 年末に自社の計算基盤へ少量から導入を開始する計画で、引き続き NVIDIA など他社のアクセラレータも調達しつつ、2027 年から規模を拡大する。
- **なぜ重要か**：マイクロソフト、Google、Amazon に続き、また 1 社のフロンティアモデルベンダーが自らカスタム推論シリコンの開発に乗り出したことになる。しかも今回は「開発中」の発表段階にとどまらず、業界標準のハードウェアと直接比較したベンチマークを初めて公開した点が新しい。「推論を均質な計算負荷として扱うのではなく、推論フェーズ特有のボトルネックを中心に設計する」という方向性は、本ナレッジベースが継続的に追跡してきた「利用率こそがハードウェア規模よりも産出を左右する」というテーマ（Dharma AI のスケジューリング研究）と呼応する——ハードウェア層とスケジューリング層が同時に「計算資源を余さず使い切る」方向へ収斂しつつある（詳細は [inference-serving](/ja/topics/inference-serving)）。
- **分類**：Models

## LangSmith Engine が issue 検知精度を倍増：本番 Agent の不具合を自動診断し修正 PR を提出する Deep Agent

- **概要**：LangSmith Engine（プラットフォーム内蔵の Deep Agent で、本番 trace を継続的にスキャンして Agent の不具合を発見・分類・診断し修正案を提示する）が性能アップグレードを発表：内部ベンチマーク IssueBench のスコアが 2 倍以上に、公開ベンチマーク Terminal-Bench（修正案の有効性を測る）が 25% 向上；累計 6000 万件超の trace をスキャンし、2 万件超の issue を特定した。検出された各 issue には証拠チェーン（失敗した実行記録、再現タイムライン、根本原因分析）、そのまま展開可能な修正 PR（prompt またはコードの変更）、オフライン検証用に整形されたグラウンドトゥルースのデータセット例、そしてその issue 専用の継続的な回帰監視が付属する。自托管デプロイ、Slack/Linear 連携、コスト削減用の「簡易分析」モードなどの新機能も追加された。
- **なぜ重要か**：これは「Agent の本番運用」が、人手で trace を巡回する形から「専用の Deep Agent が自動診断・自動修正する」形へと進化した具体的な製品化事例だ——問題を見つけるだけ（従来の可観測性でもここまではできる）ではなく、根本原因分析・修正案生成・回帰検証までの一連の流れを丸ごと自動化してパッケージ化している。本質的には「AI コードレビュー」の「問題を見つけて修正案を出す」というパターンを、人間が書いたコードではなく Agent 自身の実行軌跡に適用したものだ（詳細は [enterprise-ai-agents](/ja/topics/enterprise-ai-agents)）。
- **分類**：Agent
- **関連 Topic**：[enterprise-ai-agents](/ja/topics/enterprise-ai-agents) ・ [agent-evaluation](/ja/topics/agent-evaluation)
- **出典**：https://www.langchain.com/blog/new-in-langsmith-engine-2x-better-issue-detection

## LangChain が Agent 評価環境とタスクの構築手法を公開：Spec 生成 + Spec2Task の 2 段階パイプライン

- **概要**：LangChain が Agent 評価タスクセットを構築する社内手法を公開した——「タスクを作る」工程を 2 段階に分割する：人間がレビューする Spec 生成段階（タスクの入力・実行環境・採点基準を Markdown で詳細に記述）と、コーディング Agent が Spec を実行可能なタスクへ自動変換する Spec2Task 段階。この分割により、タスク作成を並行して進めつつ、人間のレビューを最もコストの低い Spec 段階に集中させることができる。データセット内の全タスクで共有される「world spec」という概念——データスキーマ、API 仕様、合成データ生成スクリプト、採点方法論、本番 trace から抽出したドメインパターンなど——を導入する。検証手法には、実際の Agent でタスクを実行して環境の欠陥を洗い出すことや、モデル階層をまたいだ難易度較正のテストが含まれる。この手法は GTM 調査、コードレビュー（実際にマージされた PR ベース）、trace マイニングなどの社内ベンチマーク構築に既に活用されている。
- **なぜ重要か**：「実タスク由来ベンチマーク」の方法論が、結果を公表するだけでなく「実際にどうタスクを作るか」というエンジニアリング工程そのものを体系的に分解した初めての事例だ——「人間がレビューする仕様」と「Agent が自動変換して実行する」を分離することは、ベンチマーク構築自体をエンジニアリング化・スケール可能にする具体的な道筋である（詳細は [agent-evaluation](/ja/topics/agent-evaluation)）。
- **分類**：Agent
- **関連 Topic**：[agent-evaluation](/ja/topics/agent-evaluation)
- **出典**：https://www.langchain.com/blog/building-agent-environments-and-tasks

## LangChain が OpenWiki の自己校正記憶を発表：各知識にバージョン管理された証拠を紐づけ、コード変更時に自動で「要確認」フラグ

- **概要**：LangChain が OpenWiki（Agent がコードリポジトリを解析して Wiki ドキュメントを自動生成・維持するシステム）の自己校正記憶の設計を公開した。核心的な洞察は「記憶システムの良し悪しは『忘れる』能力にかかっている」というものだ——コードベースは絶えず進化し、以前は正確だったドキュメントも古くなる。しかし従来の記憶システムには「裏付けとなる証拠が変化したかどうか」を検知する仕組みがなく、記憶のドリフトや汚染を招いていた。OpenWiki はすべての事実的な陳述を「声明＋バージョン管理された証拠参照」として表現する；実行時には保存された証拠のバージョンと現在のコードを比較し、コードが変更されると依存する声明を（削除するのではなく）「要確認」としてフラグ付けする；次回の Wiki 更新時には要確認の声明が自動的に表面化して再検証され、証拠がまだ有効ならバージョン番号を更新し、無効になっていれば声明とドキュメントの両方を更新する。2,000 件の声明でテストしたところ、古い声明の割合はベースラインの 3.5% から 0.5% に、幻覚的な声明は 0.7% から 0% に低下した。
- **なぜ重要か**：これは記憶インフラの中核的な工学課題である「記憶の S/N 比管理」への具体的な解法だ——これまでの記憶に関する議論の多くは「どれだけ与えるか、どう投入するか」（ALTK-Evolve の系譜）に焦点を当ててきたが、OpenWiki は「覚えていたことが古くなったらどうするか」という欠けていたピースを埋め、「証拠のバージョン管理＋要確認フラグ」によって「全部信じるか全部消すか」という乱暴な扱いを置き換えている（詳細は [agent-memory](/ja/topics/agent-memory)）。
- **分類**：Agent
- **関連 Topic**：[agent-memory](/ja/topics/agent-memory)
- **出典**：https://www.langchain.com/blog/self-correcting-memory-openwiki

## Multiverse Computing が量子化認識修復（QAH）を発表：4-bit 圧縮モデルが自身の 16-bit 元モデルを上回る

- **概要**：Multiverse Computing が量子化認識修復（Quantization-Aware Healing、QAH）を提案した——構造的圧縮（層/ヘッドの削減）と量子化の両方を受けたモデルのための回復技術だ。すでに劣化した圧縮後チェックポイントを教師としてタスク損失を使う通常の量子化認識訓練（QAT）とは異なり、QAH は圧縮前の元のフル精度モデルから直接蒸留する——冻結された教師の logits と KL ダイバージェンス損失を用いる。教師の出力分布はアーキテクチャに依存しないため、生徒モデルが小さくても知識を効果的に移転できる。安定性については、生徒が教師に一致した後は KL ダイバージェンスにそれ以上ドリフトする動機を与えないのに対し、クロスエントロピー目的関数はハードラベルへ押し続け、継承した能力を徐々に侵食する；QAH は約 100 訓練ステップでピークに達しそのまま安定するが、QAT は約 700 ステップ後に崩壊し 19 ポイント近く低下する。GPT-OSS 120B→60B（MXFP4）での実測では、4-bit QAH モデルが 9 個のベンチマークのうち 7 個で自身の 16-bit 元モデルを上回った（例：推論ベンチマーク AA-LCR で 42.7 対 35.3、数学の AIME 2025 で 76.3 対 70.7）、同時に重みメモリは約 4 分の 1 に、token あたりの計算量は半分になった。
- **なぜ重要か**：「圧縮後のモデルが圧縮前の自分自身を上回る」というのは直感に反するが再現可能な結果だ——鍵となる洞察は「どの教師を使うか」にある：すでに劣化した回復済みチェックポイントを教師にすると生徒はより低い天井に固定されてしまうが、圧縮前の元モデルに立ち返ることで本当にその天井を突破できる。これは 08-19 の QAD、08-20 の DSpark と並ぶ「エッジ/量子化モデルを品質を落とさず高速化する」効率クラスタの 3 つ目の具体的な解法であり、3 つの中で最も直感に反する結果だ（詳細は [model-efficiency](/ja/topics/model-efficiency)）。
- **分類**：Models
- **関連 Topic**：[model-efficiency](/ja/topics/model-efficiency)
- **出典**：https://huggingface.co/blog/MultiverseComputingCAI/quantization-aware-healing

## IBM が Granite 4.2 を発表：Apache 2.0 のオープン推論モデルファミリー、実環境での強化学習で Agentic 能力を訓練

- **概要**：IBM が Granite 4.2 を発表した——同社初の「密な decoder-only 推論 LLM」ファミリーで、3B/8B/30B の 3 サイズ、すべて Apache 2.0 ライセンス。思考/非思考の切り替えと、単純なクエリ向けの低負荷モードに対応する；3 サイズとも同一のアーキテクチャを採用——グループ化クエリアテンション（40 ヘッド/8 KV ヘッド）、RoPE、SwiGLU フィードフォワード層、RMSNorm、512K のコンテキストウィンドウ。訓練パイプライン：約 15 兆 token の 5 段階事前訓練；720 万サンプル（約 1000 億 token）の教師ありファインチューニング（31.6% が Agentic データで、ソフトウェアエンジニアリング、ツール呼び出し、推論タスクを含む）；そして核心的な革新として、単一の RL パスではなく多段階の連鎖的強化学習——基礎 RL（検証可能な報酬＋スキルブースター）の後、8B/30B 限定の Agentic RL 段階で、実際にサンドボックス化されたリポジトリ・ターミナル・ブラウザの中で SWE Agent、ターミナル操作、Web 検索を訓練する（シミュレーションではない）、その後 RLHF によるアライメント——独立した価値ネットワークを持たず、グループ相対アドバンテージとリーブワンアウトベースラインを用いる非同期 GRPO を使用する。主要なベンチマーク：30B モデルは AIME25 で 89.17%、SWE-Bench Verified で 57% を達成；FP8/FP4/GGUF での量子化デプロイと 12 言語に対応し、OpenCode、Pi、OpenHands などのフレームワークとネイティブに互換性のあるツール呼び出しを備える。
- **なぜ重要か**：この発表で最も注目すべき方法論上の選択は、シミュレーションではなく実際のサンドボックス環境で Agentic RL を訓練していることだ——Agent の能力訓練を「モデルに正しい答えを言わせる」ことから「実際のターミナル/リポジトリ/ブラウザの中で物事を実際にやり遂げさせる」ことへと前進させている。本ナレッジベースがこれまで繰り返し追跡してきた「評価には実環境を使う」という流れ（ADR-Bench、実際にマージされた PR）に続き、訓練側でも合成シミュレーションではなく実環境を使い始めている；小〜中規模のパラメータ数での完全な Apache 2.0 オープン化も、「費用対効果の高いオープン推論モデル」という製品路線を継続するものだ（詳細は [deep-agents](/ja/topics/deep-agents)）。
- **分類**：Models
- **関連 Topic**：[model-efficiency](/ja/topics/model-efficiency) ・ [deep-agents](/ja/topics/deep-agents)
- **出典**：https://huggingface.co/blog/ibm-granite/granite-4-2
