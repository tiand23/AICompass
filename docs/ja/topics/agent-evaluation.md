# Agent Evaluation

## 概要

エージェント評価：実際の副作用を伴う多段階タスクでのエージェントの性能を測る方法とベンチマーク。従来のモデルベンチマーク（一問一答の採点）と異なり、軌跡が一意でない、結果が多様、タスクがオープンエンドという難題に直面する。現在の主流は「実タスク由来のサンプル + LLM-as-judge によるベースライン照合」。

## なぜ重要か

エージェントを本番投入できるかは最終的に評価が決める——再現可能な評価なしでは、プロンプト調整もモデル交換もツール変更もすべて盲目的なチューニングになる。ベンチマークは業界の「進捗バー」でもある：ReviewBench は現在のモデルが人間レビューベースラインの約 30% しか回収できないことを示し、コードレビューエージェントが飽和にほど遠いこと、改善余地がどこにあるかを定量化した。

## コアコンセプト

- **実タスク由来ベンチマーク**：本番データ（実際の PR レビューコメント、実際のチケット）から実質的なサンプルを厳選してタスクを構築——合成タスクより実際の水準を反映する（ReviewBench の手法）。
- **網羅率 vs 精度**：エージェント評価の 2 つの基本軸——漏れなく見つけたか（coverage）と報告が正確か（precision）。通常 F1 で総合。レビュー系エージェントでは特に重要で、誤検知はユーザーの信頼を直接消耗する。
- **LLM-as-judge**：エージェントの出力と人間ベースラインが同じ問題を突いているか（字面一致ではなく意味的等価）をモデルで照合——オープンエンドなタスク採点の主流方式。judge 自体のバイアスに注意。
- **戦略は変数**：同じモデルでも評価目的に合わせた構造化プロンプトでスコアが顕著に向上する——評価対象は「モデル + 戦略」の全体であり、モデル単体ではない。
- **その領域のトップ企業自身が構築する垂直ベンチマーク**：Harvey LAB（法律、24 実務分野、1,671 タスク）は ReviewBench（コードレビュー）と同じパターンを踏襲——その領域を深く手がける企業が自ら全通過基準の実タスクベンチマークを構築し、汎用の第三者ベンチマークより業界の深部の実態に近い。専門サービス系エージェント（法務/財務/医療）評価に共通する路線。
- **大規模な実研究タスクをストレステストとする**：ICML 2026 可復現性ハッカソンでは 1,221 人がコーディング Agent を使って 2,226 篇の論文（会議採択総数の 34%）の核心的主張を複現し、自動化された裁判モデルが統一的に「検証済み/反証済み/玩具規模のみ/判定不能」を判定した——「実タスク由来ベンチマーク」の方法論をオープンエンドな研究複現シナリオに適用した極限規模のサンプルであり、定量ベースラインは検証対象論文の 51% が少なくとも 1 件の主張を検証済み、23% が反証または異論ありというもの；結論は、最も信頼できる結果は人間が回路に入ることから生まれるのであって、Agent の完全自律判定ではないことを強調する。
- **専用の裁判モデルがフロンティアモデルに代わって評価を行う**：自前で LLM-as-judge を構築する代わりに、評価ツールチェーンのベンダーが「専門的に訓練された判定モデル」をそのままマネージドサービスに仕立てられる——LangSmith が最初に公開した Tuned Evaluator である Perceived Error は、ラベル付き対話データで事後学習され、判定精度ですべてのフロンティアモデルを上回りつつコストを 82%（一部のシナリオでは 98%）削減する；「垂直的な場面にフロンティア級の知能は不要」という効率哲学が評価ツール自体にまで及んでいる。
- **ベンチマーク「刷分」の検知**：公開ベンチマークで高スコアを出すことは、真のタスク能力を証明しない——モデルは単に「自分がどのベンチマーク上にいるか」を認識し、ベンチマーク特有のパターンを再現することを学習しただけかもしれない。参照分岐、遮蔽エンティティの回復率、正書法の使い分けなどの探針でこの種のデータセット指紋識別を検知できる（ASR 領域の具体的な方法論、詳細は [voice-agents](/ja/topics/voice-agents)）。
- **生成型 LLM-as-judge に代わる構造化判定モデル**：Jev はテキストの判定を生成せず型付きの判定結果を直接返す——500 件の実際の Agent 決定を繰り返し判定させた結果、全件で人間レビュアーの判定と一致し、連続的な品質スコアの分散は主流の LLM judge より 92〜913 倍低く、コストとレイテンシも 2 桁低い；ただし構造化判定モデルも prompt injection によって判定が左右されうる——免疫があるわけではない。
- **帰属の正しさは事実の正しさとは独立した評価次元である**：MCP Agent が複数のツール呼び出しを組み合わせて回答を構成する場合、「その主張が何らかの証拠に支持されているか」（事実の正しさ）と「その主張が引用している出典が実際にその証拠であるか」（帰属の正しさ）は別の問題——支持度だけを見る事実検証手法は「クロスソース混同」エラー（主張は真だが誤った出典に帰属している）を見逃してしまい、専用の出典認識型検証が必要になる（詳細は [mcp](/ja/topics/mcp)）。
- **自己申告ではなくシステムの終状態で Agent を評価する**：最終回答も正しいツール呼び出しもあくまで代理指標であり、Agent は正しく聞こえる発言をしながら間違った値を書き込んだり間違ったレコードを変更したり余計な副作用を生んだりしうる；ThinkingBox は Agent がデータベースに残した終状態と副作用を直接検査し、同じタスクを 20 回繰り返すことで「安定して成功できるか（運良く一度成功しただけではないか）」という、これまで単独では測定されにくかった次元を定量化した——「Agent 自身が言っていることをそのまま信じない」という方法論（出典の帰属を検証する ProvenanceGuard に続く）を「システム状態の実際の変化」という対象に拡張したもの。
- **意思決定/判定が独立した専用モデル品類へ分化しつつある**：LangChain の Jev（09-21）、OpenAI の Decisions API（10-06、GPT-6 Luna 駆動）、LiquidAI の d1（10-07、単一の順伝播で確定的な答えを返す）——背景の異なる 3 社が 1 か月のうちに構造的に一致した解法に到達した：狭く定義された質問、型付き出力、汎用的な対話呼び出しよりはるかに低いコスト/レイテンシ；分類・ルーティング・Agent の次の行動決定といったタスクは、もはや「汎用 LLM を呼んでテキストの答えを解析する」がデフォルトではなくなり、評価/選定の際には専用の決定モデルを LLM-as-judge と並ぶ独立した選択肢として検討すべきである。
- **評価タスクそのものの構築手法**：「タスクを作る」工程を、人間がレビューする Spec 生成段階（入力/環境/採点基準を Markdown で記述）と Agent が自動実行する Spec2Task 変換段階に分割し、タスク作成を並行して進めつつ人間のレビューを最もコストの低い段階に集中させる；タスク間で共有される「world spec」（データスキーマ、採点方法論、ドメインパターン）がタスク作成の重複コストをさらに削減する——「実タスク由来ベンチマーク」の方法論を「実際にどうタスクを作るか」というエンジニアリング工程で体系化するもの。

## ベストプラクティス

- 評価セットはまず自分の実際の失敗事例から作る。汎用ベンチマークのスコアと自分のシナリオの相関はしばしば限定的。
- プロンプト/戦略も A/B の評価対象に含める——「モデルがダメ」の多くは実は「戦略がダメ」。
