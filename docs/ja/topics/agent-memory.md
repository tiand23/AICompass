# Agent Memory

## 概要

エージェント記憶：エージェントがセッションやタスクを跨いで情報を保持・再利用するためのインフラレイヤー——セッション内のコンテキスト管理から、長期記憶（ユーザー嗜好、意思決定履歴）、チームレベルの共有記憶資産まで。代表プロジェクト/製品：Mem0、Zep、LangMem（LangChain）、そして記憶をチーム資産ハブに仕立てた TencentDB-Agent-Memory。

## なぜ重要か

コンテキストウィンドウがどれだけ大きくても、それは「作業記憶」にすぎない——エージェントがユーザーやチームに長期的に仕えるには、単一セッションから独立した記憶レイヤーが必要。記憶の質はエージェントの「熟練度」を直接決める：嗜好を覚えないアシスタントは毎回ゼロから始め、意思決定履歴を忘れるエージェントは同じ失敗を繰り返す。チームレベル記憶（テンセントの 4 資産アーキテクチャなど）はさらに個人の経験を組織資産に変える——エンタープライズエージェント導入の鍵となるピース。

## コアコンセプト

- **階層化記憶アーキテクチャ**：生会話（L0）から要約・事実・ペルソナ/嗜好（L3）へ段階的に蒸留——保存粒度と検索コストの階層的トレードオフ（TencentDB-Agent-Memory の Chat Memory 階層が典型的実装）。
- **記憶資産のタイプ**：会話記憶だけではない——スキル（実行可能な手順）、知識（Wiki/ドキュメント）、コードグラフ（シンボルと呼び出し関係）もすべて資産化でき、それぞれ抽出・検索方法が異なる。
- **書き込みポリシー**：何を記憶すべきか（明示指示 vs 自動抽出）、いつ更新し、いつ忘却/失効させるか——記憶の S/N 比管理がエンジニアリング上の難所。
- **権限とスコープ**：チームレベル記憶には RBAC（private/team/restricted）とエージェントごとの紐付け（loadout）が必要で、グローバル注入は不可——記憶の越権は新しいセキュリティ面。
- **RAG との関係**：技術スタックは大きく重なる（ベクトル検索、構造化ストレージ）。違いはデータソースとライフサイクル——RAG は静的なナレッジベースを検索し、記憶は対話から継続的に成長する。
- **経験記憶の投入戦略**：実行トレースから「教訓」を抽出する際は、要約に圧縮しない（情報を失う）——支持回数で追跡した逐条の詳細を保持する。しかし検索・投入の段階は全量ダンプではなく選択的に行うべき——ALTK-Evolve の「高支持度の小さなコア + タスク関連の選択」は、ACE の「毎ステップ全 playbook を注入」に比べて token を 60〜85% 削減しつつ、精度は維持または向上する（特に弱いモデル/難しいタスクでは、長すぎるコンテキストが判断を損なう）。

## ベストプラクティス

- ソリューション選定の前に「何を記憶するか」を分類する：嗜好類は少量で構造化保存に向き、経験類は雑多で抽出パイプラインが必要。会話ログの原文をすべてベクトル DB に流し込んで記憶と呼ばない。
- 記憶の書き込みには S/N 比のゲート（レビュー、確信度閾値）を設ける——汚れた記憶は記憶がないより悪い。

## Timeline

### [2026-08-11](/ja/today/2026-08-11)

IBM Research が ALTK-Evolve をオープンソース化：ACE（Agentic Context Engineering）と根本発想は同じ——どちらも実行トレースから「教訓」を抽出し、要約に圧縮せず支持回数で追跡した逐条の詳細を保持する——が、投入方法が異なる：ACE は毎ステップ全 playbook を注入し、ALTK-Evolve は高支持度ガイドラインの小さなコアを土台にタスク関連の選択を追加する。AppWorld ベンチマークでは、DeepSeek-V3.2 が ACE の約 40% の token コストでより高い精度（89.3% vs 80.4%）を達成；弱いモデルの gpt-oss-120b では精度はほぼ互角で ACE の約 7 分の 1 の token 数で済んだ。
