# Agent Memory

## 概要

エージェント記憶：エージェントがセッションやタスクを跨いで情報を保持・再利用するためのインフラレイヤー——セッション内のコンテキスト管理から、長期記憶（ユーザー嗜好、意思決定履歴）、チームレベルの共有記憶資産まで。代表プロジェクト/製品：Mem0、Zep、LangMem（LangChain）、そして記憶をチーム資産ハブに仕立てた TencentDB-Agent-Memory。

## なぜ重要か

コンテキストウィンドウがどれだけ大きくても、それは「作業記憶」にすぎない——エージェントがユーザーやチームに長期的に仕えるには、単一セッションから独立した記憶レイヤーが必要。記憶の質はエージェントの「熟練度」を直接決める：嗜好を覚えないアシスタントは毎回ゼロから始め、意思決定履歴を忘れるエージェントは同じ失敗を繰り返す。チームレベル記憶（テンセントの 4 資産アーキテクチャなど）はさらに個人の経験を組織資産に変える——エンタープライズエージェント導入の鍵となるピース。

## コアコンセプト

- **階層化記憶アーキテクチャ**：生会話（L0）から要約・事実・ペルソナ/嗜好（L3）へ段階的に蒸留——保存粒度と検索コストの階層的トレードオフ（TencentDB-Agent-Memory の Chat Memory 階層が典型的実装）。
- **記憶資産のタイプ**：会話記憶だけではない——スキル（実行可能な手順）、知識（Wiki/ドキュメント）、コードグラフ（シンボルと呼び出し関係）もすべて資産化でき、それぞれ抽出・検索方法が異なる。
- **書き込みポリシー**：何を記憶すべきか（明示指示 vs 自動抽出）、いつ更新し、いつ忘却/失効させるか——記憶の S/N 比管理がエンジニアリング上の難所。
- **権限とスコープ**：チームレベル記憶には RBAC（private/team/restricted）とエージェントごとの紐付け（loadout）が必要で、グローバル注入は不可——記憶の越権は新しいセキュリティ面。
- **RAG との関係**：技術スタックは大きく重なる（ベクトル検索、構造化ストレージ）。違いはデータソースとライフサイクル——RAG は静的なナレッジベースを検索し、記憶は対話から継続的に成長する。
- **経験記憶の投入戦略**：実行トレースから「教訓」を抽出する際は、要約に圧縮しない（情報を失う）——支持回数で追跡した逐条の詳細を保持する。しかし検索・投入の段階は全量ダンプではなく選択的に行うべき——ALTK-Evolve の「高支持度の小さなコア + タスク関連の選択」は、ACE の「毎ステップ全 playbook を注入」に比べて token を 60〜85% 削減しつつ、精度は維持または向上する（特に弱いモデル/難しいタスクでは、長すぎるコンテキストが判断を損なう）。
- **記憶のベンダー横断可搬性**：これまでの記憶に関する議論は主に「同じ Agent/同じベンダー内でどうセッションを跨いで記憶するか」に焦点を当ててきた——ai-memory はその範囲を「別のベンダーの Agent に切り替えても記憶を持ち運べるか」へと広げている：生の会話ログを保存する代わりにライフサイクルイベントを脱敏し、検索可能な Markdown wiki に編纂し、異なる Agent（Claude Code、Codex、Cursor など）ごとに個別のフックアダプタを実装しつつ、すべて同じ記憶サービスに書き込むことで、ベンダー横断の引き継ぎを実現している；「記憶システムを持つこと」と「大型モデルを使う余裕があること」を切り離すゼロ LLM モードも提供する。
- **記憶の投入はモデル階層ごとに較正すべきで、一律ではない**：IBM Research のフォローアップ研究（8 モデル、117B〜745B パラメータ、AppWorld 585 タスク）は「記憶は多いほど良い」が成立しないことを示した——余力のある強いモデル（DeepSeek-V3.2）は完全なガイドライン注入から最も恩恵を受ける；より弱い/小さいモデル（gpt-oss-120b）はむしろ精選検索の方が成績が良い（精度向上が大きく、token 消費も少ない）；既に飽和したモデル（GLM-5）はどちらの投入方式でも向上しない。記憶の最適化は本質的に「投与量の較正」であり、情報量の最大化ではない——投入戦略は対象モデルの能力階層ごとに調整する必要がある。
- **記憶システムの良し悪しは「忘れる」能力にかかっている**：コードや知識は絶えず進化し、以前は正確だった記憶も古くなるが、従来の記憶システムには裏付けとなる証拠が変化したかを検知する仕組みがなく、記憶のドリフトや汚染を招く；OpenWiki はすべての陳述を「声明＋バージョン管理された証拠参照」として表現し、元となるソースが変化すると依存する声明を削除も維持もせず自動で「要確認」フラグを付け、次回の更新時に再検証する。「全部信じるか全部消すか」を「証拠のバージョン管理＋要確認フラグ」に置き換えた結果、テストでは古い声明の割合が 3.5% から 0.5% に、幻覚的な声明が 0.7% から 0% に低下した。

## ベストプラクティス

- ソリューション選定の前に「何を記憶するか」を分類する：嗜好類は少量で構造化保存に向き、経験類は雑多で抽出パイプラインが必要。会話ログの原文をすべてベクトル DB に流し込んで記憶と呼ばない。
- 記憶の書き込みには S/N 比のゲート（レビュー、確信度閾値）を設ける——汚れた記憶は記憶がないより悪い。

## Timeline

### [2026-08-25](/ja/today/2026-08-25)

LangChain が OpenWiki の自己校正記憶の設計を公開：各声明にバージョン管理された証拠参照を紐づけ、コードが変更されると依存する声明を削除せず「要確認」としてフラグ付けし、次回の更新時に自動で再検証する。2,000 件の声明でのテストでは、古い声明の割合が 3.5% から 0.5% に、幻覚率が 0.7% から 0% に低下し、コストは累積声明数ではなくコード変更量に比例した——「覚えていたことが古くなったらどうするか」という記憶の S/N 比管理の欠けていたピースを埋めるものだ。

### [2026-08-19](/ja/today/2026-08-19)（補漏）

Claude Managed Agents の自托管サンドボックスセッションが記憶ストアの接続に対応：SDK worker がセッション開始時に接続された記憶ストアをサンドボックス内にダウンロードし、Agent が生じた変更をストアへ同期する——これまで API レベルの能力にとどまっていた Agent の記憶をホスト型実行環境自体に落とし込み、記憶の読み書きをサンドボックスのライフサイクルに直接結び付けた。

### [2026-08-18](/ja/today/2026-08-18)

IBM Research が ALTK-Evolve のフォローアップ研究を発表：8 モデル（117B〜745B パラメータ）が AppWorld の 585 タスクで、「記憶をどれだけ与えるべきか」がモデル階層によって異なることを示す——強いモデル（DeepSeek-V3.2）は完全なガイドライン注入でタスク完了率が 9.5 ポイント向上；弱いモデル（gpt-oss-120b）は精選検索で 16.1 ポイント向上し token 消費増は 5% に留まる；飽和したモデル（GLM-5）はどちらの方式でも向上幅は 0。記憶の最適化は「情報量の最大化」ではなく「投与量の較正」として理解すべきだ。

ai-memory がオープンソース化：コーディング Agent 向けの長期記憶レイヤーで、ベンダーを跨いだシームレスな引き継ぎを中心に設計されている（Claude Code をタスク途中で終了し、同じディレクトリで Codex に切り替えても、アーキテクチャを再説明せず作業を継続できる）；セッションのライフサイクルイベントを脱敏して Markdown wiki に編纂し、Claude Code/Codex/Cursor などそれぞれに個別のフックアダプタを実装しつつ同じ記憶サービスを共有；ゼロ LLM モードも提供する（詳細は [coding-agents](/ja/topics/coding-agents)）。

### [2026-08-11](/ja/today/2026-08-11)

IBM Research が ALTK-Evolve をオープンソース化：ACE（Agentic Context Engineering）と根本発想は同じ——どちらも実行トレースから「教訓」を抽出し、要約に圧縮せず支持回数で追跡した逐条の詳細を保持する——が、投入方法が異なる：ACE は毎ステップ全 playbook を注入し、ALTK-Evolve は高支持度ガイドラインの小さなコアを土台にタスク関連の選択を追加する。AppWorld ベンチマークでは、DeepSeek-V3.2 が ACE の約 40% の token コストでより高い精度（89.3% vs 80.4%）を達成；弱いモデルの gpt-oss-120b では精度はほぼ互角で ACE の約 7 分の 1 の token 数で済んだ。
