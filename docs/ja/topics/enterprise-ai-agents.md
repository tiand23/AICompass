# Enterprise AI Agents

## 概要

エンタープライズにおける AI エージェントの実装：ホスト型プラットフォームとランタイム、デリバリーモデル（自前構築 / プラットフォーム / 常駐型デリバリー）、権限・評価・運用のエンジニアリングプラクティス。OpenAI Presence、Claude Managed Agents などのプラットフォームを対象とする。

## なぜ重要か

「生成 AI の企業導入」の主戦場。モデル能力が収斂するにつれ、競争はデリバリーと運用へ移る：エージェントを企業システムに確実に接続し、ポリシーに従って行動させ、失敗時に人間へエスカレーションできるのは誰か。開発者にとって、プラットフォームベンダーの動向は「作る」と「買う」の境界線を決める。

## コアコンセプト

- **デリバリーモデルのスペクトラム**：純粋な API 自前構築 → ホスト型ランタイム（Managed Agents）→ プラットフォーム + 常駐エンジニア（Presence の FDE モデル）。
- **ポリシーと権限**：企業が定義する policy・permission・評価基準がエージェントの行動を制約する。人間へのエスカレーションは標準装備。
- **運用成熟度のシグナル**：ライフサイクル webhook、セッション初期投入、ストリーミング観測——プラットフォームの成熟度を測る具体的な API 能力。セッション単位の予算ハード上限とデータ所在地制御が、このシグナル群の最新の追加項目。
- **「own your intelligence」論争**：インテリジェンスをプラットフォームに委ねるか、自社に留めるか——エンタープライズ AI アーキテクチャの核心的分岐。
- **「人事管理」メンタルモデルの移植**：エージェント数が増えると、チームは従業員を管理するのと同じやり方でエージェントを管理し始める——チケット割当、組織構造（ロール/報告ライン）、予算強制、ガバナンス承認フロー、監査ログ（Paperclip の事例）。Managed Agents の予算/権限能力とエージェントワークフローオーケストレーションを 1 つの統一管理プレーンへ統合しようとするプロダクト化の試み。
- **コスト統治の 3 つの速度**：ランタイム最適化（各リクエストをリアルタイムで適切な規模のモデルにルーティング）、ワークフロー最適化（日/週単位のテストで Agent 効率を改善）、継続的ガバナンス（要求に応じて緩めることのない支出上限）——3 つの異なるペースは二者択一ではなく並行して走らせる必要があり、これまで散らばっていたコスト削減手段（ルーティング、キャッシュ、評価駆動の改善、支出のハード上限）を 1 つのフレームワークに整理する発想（Azure が提唱）。付随する自己点検：モデル/Agent/ワークフロー別にコストを可視化できるか？リクエストが不必要に高性能なモデルへ過剰投入されていないか？Agent 効率が継続的に改善する仕組みがあるか？利用急増時に支出上限を強制できるか？
- **コンプライアンスの中間解としての実行ローカル化**：Claude Code の自托管 runner はソースの checkout とビルド成果物を顧客ネットワーク内に留める一方、prompt/会話内容は依然クラウドへ推論のため送られる——「完全マネージド」と「完全自前構築」の間にあるより細かい第 3 の選択肢で、「ソースコードはイントラネットの外に出せないが、内容をベンダー推論に送ることは許容できる」という企業でよくあるコンプライアンス上の一線に直接対応する（詳細は [coding-agents](/ja/topics/coding-agents)）。

## ベストプラクティス

- デリバリースペクトラム上の自社の位置を見極める：プラットフォームエンジニアリングの余力があればホスト型ランタイム、人手不足なら常駐型デリバリーの費用対効果を評価。
- どのモデルを選んでも、権限の階層化と人間エスカレーションの仕組みは自社で掌握する——プラットフォームに全面委任しない。
