## OpenAI 与 Broadcom 发布 Jalapeño 推理芯片实测结果：吞吐效率、延迟均超 NVIDIA Blackwell

- **一句话总结**：OpenAI 与 Broadcom（2025-10 官宣合作）联合研发的定制推理芯片 Jalapeño 公布首批实测数据。芯片针对推理阶段专门设计——围绕 prefill（预填充）与通信阶段的瓶颈做架构优化，最小化数据搬运与通信延迟，模型状态（含生成过程用到的 KV cache）可显式本地化存放。用 SemiAnalysis 的 InferenceX 基准，在 GPT-OSS 120B、DeepSeek R1 670B、Kimi K2.5 1T 三个模型上测试，相比 NVIDIA Blackwell 系统（GB200/GB300），Jalapeño 每瓦特峰值算力提升 1.5-1.9 倍、端到端延迟降低 1.7-3.6 倍；高交互性负载场景性能提升达 2.1-4.1 倍。OpenAI 计划 2026 年底小批量部署进自有算力基础设施，同时继续采购 NVIDIA 等厂商加速器，2027 年起扩大规模。
- **为什么重要**：这是继微软、Google、Amazon 之后又一家前沿模型厂商亲自下场做定制推理芯片，且是首次公开对标行业标杆硬件的实测基准而非仅停留在"研发中"阶段。"围绕推理阶段特有瓶颈做架构设计"这一取向，与知识库持续跟踪的"利用率而非硬件规模决定产出"（Dharma AI 调度研究）形成呼应——硬件层与调度层正同时朝"把每一分算力都用在刀刃上"收敛（详见 [inference-serving](/topics/inference-serving)）。

## LangSmith Engine issue 检测能力翻倍：Deep Agent 自动诊断生产 Agent 故障并提交修复 PR

- **一句话总结**：LangSmith Engine（平台内置 Deep Agent，持续扫描生产 trace 自动发现、归类、诊断 Agent 故障并给出修复方案）公布性能升级：内部基准 IssueBench 得分翻倍以上，公开基准 Terminal-Bench（衡量修复方案有效性）提升 25%；累计扫描 6000 多万条 trace，识别出 2 万多个 issue。每个 issue 附带证据链（失败运行记录、复现时间线、根因分析）、可直接部署的修复 PR、供离线验证的标注数据集样例，以及针对该 issue 的持续回归监控。新增自托管部署、Slack/Linear 集成、省成本的"精简分析"模式等功能。
- **为什么重要**：这是"Agent 生产运维"从人工巡检 trace，向"专用 Deep Agent 自动诊断+自动修复"演进的一个具体产品化案例——不只是发现问题，而是把根因分析、修复方案生成、回归验证整个链路打包自动化，本质是把"AI 代码评审"里"发现问题+给出修复建议"的模式，从人写的代码搬到 Agent 自身的运行轨迹上（详见 [enterprise-ai-agents](/topics/enterprise-ai-agents)）。

## LangChain 分享 Agent 评估环境与任务的构建方法论：Spec 生成 + Spec2Task 两阶段流水线

- **一句话总结**：LangChain 发文介绍内部构建 Agent 评估任务集的方法论——把"造题"拆成两阶段：人工把关的 Spec 生成阶段（Markdown 详细描述任务输入、执行环境、评分细则），再用编码 Agent 自动把 Spec 转换成可执行任务（Spec2Task）；这一拆分让任务创建可并行进行，同时把人工审核集中在成本最低的 Spec 阶段。提出"world spec"概念——跨任务共享的项目级信息（数据 schema、API 规范、合成数据生成脚本、评分方法论）。验证手段包括用真实 Agent 跑任务找环境缺陷、跨模型档位测试难度校准。已用该方法论构建 GTM 调研、代码评审（基于真实已合并 PR）、trace 挖掘等内部基准。
- **为什么重要**：这是"真实任务派生基准"方法论第一次系统性拆解出"怎么造题"本身的工程流程，而不只是造完题公布结果——把"人工把关的规格"与"Agent 自动转换执行"分离，是评估基准构建这件事本身走向工程化、可规模化的具体路径（详见 [agent-evaluation](/topics/agent-evaluation)）。

## LangChain 发布 OpenWiki 自我校正记忆机制：给每条知识配版本化证据，代码变更后自动标记"存疑"

- **一句话总结**：LangChain 分享 OpenWiki（用 Agent 分析代码仓库自动生成并维护 Wiki 文档的系统）的自我校正记忆设计。核心洞察："记忆系统的好坏取决于它能不能'忘记'"——代码库持续演进，此前准确的文档会过时，传统记忆系统缺乏检测"支撑证据是否已变化"的机制，导致记忆漂移。OpenWiki 把每条陈述表示为"声明+版本化证据引用"；运行时对比证据版本与当前代码，代码变更后相关声明标记为"存疑"（而非直接删除）；下次更新时自动浮现存疑声明并重新核验，证据仍成立则刷新版本号，已失效则同步更新声明与文档。实测 2000 条声明：过期声明占比从 3.5%（基线）降至 0.5%，幻觉声明从 0.7% 降至 0%。
- **为什么重要**：这是"记忆信噪比管理"这一记忆基础设施核心难题的一个具体解法——此前记忆讨论多聚焦"该记多少、怎么投喂"，OpenWiki 补上了"记住的东西过时了怎么办"这一环，用"证据版本化+存疑标记"取代"要么全信要么全删"的粗暴处理（详见 [agent-memory](/topics/agent-memory)）。
- **分类**：Agent
- **关联 Topic**：[agent-memory](/topics/agent-memory)
- **来源**：https://www.langchain.com/blog/self-correcting-memory-openwiki
