## needle 2 登场：14MB 单文件基础模型，专为手机/穿戴/机器人设计

- **一句话总结**：cactus-compute/needle（单日 +315，累计 4.6k star，MIT 协议）——一个专为手机、可穿戴设备、智能家居、机器人等资源受限环境设计的极小基础模型：整个模型是一个 14MB 的单一二进制文件，推理时只占约 28MB 内存（256 token 滑动窗口，工具定义常驻为 KV sink）。架构上用 Hadamard MLP 替代传统前馈网络、配合分组查询注意力（GQA）、基于哈希 n-gram 表的 Engram 键值记忆、多路超连接与三明治门控 RMS 归一化，并用 Cactus Quants 的 CQ2-bit 压缩把体积压到极限；论文公开在 arXiv（2607.18363）。功能上专注工具调用（带置信度打分门控执行）、大工具目录检索排序（每轮从大量候选里选出前 5 个）、按 Pydantic schema 做结构化抽取、字节级语法约束解码保证输出合法 JSON。官方数据：体积比 FunctionGemma 270M、LFM2.5 230M、Apple FM 小 5-70 倍（且是 2-bit vs 它们的 f16），效果与之互有胜负。
- **为什么重要**：这是 SLM/端侧模型这条路线上体积极限的一次刷新——14MB 单文件、28MB 运行时内存的量级，把"能跑在手表/机器人上的基础模型"从概念变成了确实可下载可运行的东西。比参数量更值得注意的是它的功能取向：不追求通用对话质量，而是专精"工具调用 + 结构化抽取"这两个 Agent 最核心的动作，并且原生做了置信度门控和大工具目录检索——这是把"资源受限设备上的 Agent"当作一个独立产品形态来设计，而不是把大模型简单缩小。
- **分类**：Models
- **关联 Topic**：[model-efficiency](/topics/model-efficiency)
- **来源**：https://github.com/cactus-compute/needle

## LlamaIndex：LLM OCR 的错误不是变少了，而是变得更难被发现

- **一句话总结**：LlamaIndex 发文指出，LLM 驱动的 OCR 与传统 OCR 的失败模式有本质区别——Tesseract 一类传统引擎出错时产出"肉眼可见的乱码"，而 LLM 出错时产出的是流畅、看似合理的文本，掩盖了缺失或错误的内容。文章拆解三种主流架构（OCR 先转文字再由 LLM 纠错、VLM 直接读图转录、按区域分割再路由到专门模型的 agentic 编排）各自独立的失败方式，核心机制是：当视觉证据模糊时，模型会偏向"语言上最可能的文本"而非"图像证据最支持的文本"；账号、零件编号等高熵字符串恰恰是语言先验最弱、因此最容易被幻觉污染的地方。文章还指出字符错误率/词错误率这类传统指标"在整页上取平均"会掩盖真正的风险——一页 99% 字符准确率，如果错的 1% 正好是总金额或编号字段，这页数据依然毫无价值。结论：生产系统需要分割、路由到专门模型、校验回路、把输出链接回源文件像素位置的引用这类架构级控制手段，光靠原始模型本身做不到。
- **为什么重要**：这是文档解析这条主线里一次重要的方法论补充——此前 08-05"OCR 不会被商品化"、08-11 ExtractBench 分别论证了"专用引擎更强"和"给出可复现横评数据"，这篇文章补上了更底层的机制解释：为什么 LLM OCR 的错误特别危险，不是因为错得更多，而是因为错得更隐蔽、更像对的。"传统整页平均指标会掩盖关键字段错误"这个洞察对任何在用 CER/WER 类指标做验收的团队都是直接可用的方法论修正——应该按字段类型（尤其高熵字段）分别测准确率，而不是看整页平均分。
- **分类**：RAG
- **关联 Topic**：[document-parsing](/topics/document-parsing)
- **来源**：https://www.llamaindex.ai/blog/llm-ocr

## 微软 Azure 提出 Agent 优化"三速模型"：运行时路由、工作流迭代、持续治理三层各自节流

- **一句话总结**：Azure 发文《The Economics of Agent Optimization》，引用微软委托 IDC 对 4000+ 企业决策者的调研（71% 计划增加 AI 预算）与超 10 万家企业已在 Microsoft Foundry 上构建这一数据背景，提出企业管理 Agent 成本应该分三种不同节奏同时进行：**运行时优化**（实时把每个请求路由到合适规格的模型）、**工作流优化**（以天/周为周期通过测试持续改进 Agent 效率）、**持续治理**（设定不会被随意放宽的支出上限）。文章给出四个自查问题（能否按模型/Agent/工作流看清成本？请求是否被过度配置到不必要的高规格模型？Agent 效率是否在随时间改进？用量激增时能否强制止损？），并点出 Microsoft Foundry 配套的具体能力：模型路由器（按成本优化请求路由）、prompt/语义缓存（复用上下文）、Agent optimizer（测试配置组合）、Azure API Management AI Gateway 的 token 速率限制。核心主张：企业该从"一次性采购智能"（零散试点）转向"持续管理智能"（全生命周期内有边界、可问责的支出）。
- **为什么重要**：这篇文章把此前分散在各处的 Agent 降本手段（模型路由、prompt 缓存、评估驱动的效率迭代、支出硬顶）第一次组织成一个"三种节奏"的统一治理框架，而不是罗列一堆孤立技巧——这个分层思路本身值得借鉴：运行时级的优化几乎零成本但收益有限，工作流级需要持续投入但收益更大，治理级不创造效率收益但兜底风险敞口，三者要同时跑而不是二选一。这也是 LangChain Switchyard 模型路由实测（08-11）在企业侧治理层面的自然延伸——把"该不该做路由"的工程判断放进了一个更完整的组织级成本管理框架里。
- **分类**：Agent
- **关联 Topic**：[enterprise-ai-agents](/topics/enterprise-ai-agents) ・ [model-efficiency](/topics/model-efficiency)
- **来源**：https://azure.microsoft.com/en-us/blog/the-economics-of-agent-optimization-from-pilots-to-measurable-returns/
