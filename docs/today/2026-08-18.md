## ai-memory 开源：编码 Agent 的长期记忆层，支持跨厂商无缝交接任务

- **一句话总结**：akitaonrails/ai-memory（单日 +207，累计约 2.1k star，MIT 协议）——面向编码 Agent CLI 的长期记忆系统，核心场景是"在 Claude Code 里中途退出任务，换到同目录下的 OpenAI Codex 继续，不需要重新给它讲一遍架构"。不存储原始对话日志，而是把会话生命周期事件（prompt、工具调用、失败记录）脱敏后提炼编译成可检索的 Markdown wiki；会话结束时生成包含"未解决问题、下一步计划"的交接摘要，下一个 Agent 在收到第一条 prompt 前会先拿到"上次进展到哪"的总结。架构上是单一 Rust 二进制管理一个数据目录（wiki 源真相/git 版本化、raw 脱敏转录、SQLite+FTS5 数据库、本地 embedding 模型、滚动日志），生命周期 hook 把事件"发后不理"式 POST 给本地 HTTP 服务器，服务器串行化写入 SQLite，编译会话页面，并通过 FTS5 全文检索+实体匹配 RRF+可选向量检索提供召回。已为 Claude Code、Codex、Command Code、Devin、OpenCode、Cursor、Kiro CLI 等实现了各自的 hook 适配——不同 Agent 的 hook schema 不同，但都把观察数据 POST 到同一个服务器，这是跨厂商交接得以实现的关键。另提供 MCP server（`memory_query`/`memory_write_page`/`memory_feedback` 等工具）、只读 Web UI，以及不依赖任何 LLM 的"零 LLM 模式"（退化为 FTS5+声明式实体+规则摘要）。
- **为什么重要**：此前记忆基础设施的讨论大多聚焦"同一个 Agent/同一个厂商内怎么记得住"，ai-memory 把范围扩大到"换一个厂商的 Agent 继续干活，记忆能不能带得走"——这是编码 Agent 生态"多工具并用成为常态"（此前 holaOS 也体现了同一趋势）之后一个自然但此前少有人做的下一步：记忆本身不应该被锁定在单一供应商的 harness 里。"零 LLM 模式"这个设计选择也值得注意——检索与摘要的基础能力不依赖任何模型调用，把"记忆系统本身"和"用不用得起大模型"解耦，是一种务实的降低使用门槛的思路。
- **分类**：Agent
- **关联 Topic**：[agent-memory](/topics/agent-memory) ・ [coding-agents](/topics/coding-agents)
- **来源**：https://github.com/akitaonrails/AI-Memory

## IBM Research 后续研究：Agent 记忆不是越多越好，而要按模型档位"校准剂量"

- **一句话总结**：IBM Research 发布 ALTK-Evolve（08-11 已收录的记忆蒸馏框架）的后续研究，专门探讨"不同规模的模型到底需要多少记忆"这个问题——核心发现推翻"记忆越多越好"的直觉。研究覆盖 8 个模型（117B 到 745B 参数）在 AppWorld（585 个跨模拟应用的多步骤任务）上的表现，用任务目标完成率（TGC）和场景目标完成率（SGC，跨任务变体的全通过可靠性）两个指标衡量，呈现三种截然不同的模式：**有余力的强模型**从完整准则注入中获益——DeepSeek-V3.2 用全量准则任务完成率提升 9.5 个百分点；**较弱/较小的模型**反而是精选检索（核心准则打底+按任务挑相关条目）表现更好——gpt-oss-120b 用精选检索比基线提升 16.1 个百分点，且只多耗 5% token；**已饱和的模型**则毫无提升——GLM-5 在两种投喂方式下提升幅度均为 0.0 个百分点，暗示存在能力天花板或准则相关性瓶颈。成本上，精选检索以极小的 token 开销换取更优准确率，而完整注入会带来 51%-78% 的 token 成本增幅（可靠 prompt 缓存策略能部分缓解生产成本）。
- **为什么重要**：这篇研究把"Agent 记忆优化"从"往上堆"重新定义为"按档位校准"——该给多少记忆取决于模型档位，而不是简单地追求信息量最大化。这是对 08-11 那篇 ALTK-Evolve 研究（"选择性投喂省 token 且不掉准确率"）的重要补充和深化：上次证明了"精选检索"这条路径本身有效，这次进一步揭示"精选检索有效"本身不是普适真理，而是因模型档位而异的现象——强模型需要的是"够用的信息量"，弱模型需要的是"够精准的信息量"，饱和模型给什么都没用。对正在设计记忆系统的团队，这意味着"一套记忆投喂策略打天下"本身可能就是错误假设，需要按目标模型的能力档位分别调优。
- **分类**：Agent
- **关联 Topic**：[agent-memory](/topics/agent-memory)
- **来源**：https://huggingface.co/blog/ibm-research/altk-evolve-hmm

## Sentence Transformers v6.0 原生支持多向量（后期交互）Embedding：ColBERT 式检索进入主流库

- **一句话总结**：Sentence Transformers v6.0 新增 `MultiVectorEncoder`，原生支持 ColBERT 式的多向量（后期交互，late-interaction）Embedding 模型——与稠密 Embedding 把整份文档压缩成一个向量不同，多向量模型给每个 token 保留一个向量（9 个 token 的文档变成 9×128 的矩阵而非 1×128 的单一向量），把"交互"推迟到打分阶段，兼具双编码器的可离线索引能力与交叉编码器式的精细查询-文档比对。打分用 MaxSim 算子：每个查询 token 在文档所有 token 里找相似度最高的一个再求和，形成"每个查询词都指向文档里最能解释它的那个词"的软对齐，能捕捉"live"和"inhabit"这种零字符重叠但语义相关（相似度 0.94）的匹配，同时不丢失精确匹配。新库原生兼容任意 PyLate 与 Stanford-NLP ColBERT 检查点、以及 ColPali 视觉文档模型，提供不对称的 `encode_query()`/`encode_document()` 接口，覆盖文本/图像/音频/视频多模态。基准数据：同等规模模型对比，NanoBEIR 上多向量版本（LateOn，0.6868 平均 NDCG@10）在 13 个数据集中的 9 个上跑赢对应的稠密版本（DenseOn，0.6764）；但存储成本高得多——编码 4,874 篇 Natural Questions 段落，稠密（MiniLM）仅需 7.5MB，多向量（128 维）原始需 311.5MB（经 PLAID 索引压缩后约 92MB）；token 池化（pool_factor=2）可把向量数减半且精度损失小于 1%。已支持 Qdrant/Weaviate/Vespa/LightOn fast-plaid 等原生索引，fast-plaid 在 4,874 篇文档上近似 PLAID 索引查询延迟约 11ms。
- **为什么重要**：这是"检索精度 vs 存储成本"这条权衡曲线上一个此前偏小众的技术路线（ColBERT 式多向量检索）首次被主流库正式收编——此前多向量检索主要停留在论文与专门库（如 PyLate），Sentence Transformers 原生支持意味着它正式进入生产级 RAG/检索栈选型的常规选项之列，而不再是需要自己拼装的实验性方案。9/13 数据集上跑赢同规模稠密模型这个结果，直接给"稠密向量压缩损失信息"这个长期被引用但缺少统一实现验证的论点提供了可复现的对照数据；存储成本高一个数量级这一点也说明这不是无代价的免费午餐，需要按自己的召回率要求和存储预算做取舍，而不是默认切换。
- **分类**：RAG
- **关联 Topic**：[vector-databases](/topics/vector-databases) ・ [rag](/topics/rag)
- **来源**：https://huggingface.co/blog/multi-vector-encoder

## LangSmith 推出"调优过的评估器"：专用小模型做 Agent 评判，比前沿模型准且省 82% 成本

- **一句话总结**：LangSmith 发布 Tuned Evaluators（调优评估器）——一种托管评估服务，把"给生产环境的 trace 自动打上有用信号"这件事从"团队自建评估器"变成"直接挂载即用"：LangChain 端到端维护一个预训练好、有版本管理的裁判模型，包办 prompt 工程、模型选型、凭证管理与基础设施，团队只需把它挂到追踪项目上。首个上线的评估器是 Perceived Error（感知错误检测）——识别"Agent 犯了错、误解了请求、或把交互带偏了方向"的对话，证据来源包括显式信号（用户纠正、拒绝）与隐式推断（自相矛盾的回复、承认错误、未解决的结果）。该模型通过在标注过的对话式 Agent trace 上做后训练得到专用能力，实测"超过所有前沿模型"的判断准确度，同时成本降低 82%——部分客户工作负载视对话构成不同，成本降幅最高达 98%。使用门槛：线程至少需要两轮人类-AI 消息对且配置了闲置期；评估结果在符合条件后 12 小时内完成；目前仅 Plus 与 Cloud Enterprise 美国区可用；只有成功执行的评估才计费，跳过或失败的评估免费。
- **为什么重要**：这是"用专用小模型替代前沿模型做 LLM-as-judge"这条降本思路在评估这个具体场景里的一次产品化落地——此前这条思路更多以研究结论或自建方案的形式出现（如 08-11 的模型路由实测），这次是评估工具链厂商亲自把它做成开箱即用的托管服务，用户不需要自己训练或维护判断模型。"比前沿模型更准、还更便宜"这个结果本身也值得记一笔：专用后训练模型在窄任务（识别对话是否出错）上超过通用前沿模型的判断力，是"垂直场景不需要前沿智能"这条效率哲学在评估领域的又一实证；这也延续了知识库反复出现的"垂直基准由该领域参与者自建"模式——这次是评估工具本身而非评估基准被专用化。
- **分类**：Agent
- **关联 Topic**：[agent-evaluation](/topics/agent-evaluation)
- **来源**：https://www.langchain.com/blog/introducing-langsmith-tuned-evaluators-starting-with-perceived-error
