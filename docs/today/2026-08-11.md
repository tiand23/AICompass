# 2026-08-11

## LlamaIndex 发布 ExtractBench：370 份真实企业文档、14 套系统的抽取横评

- **一句话总结**：LlamaIndex 推出 ExtractBench——一个开放基准，在 370 份真实企业文档上测试 14 套抽取系统，按完整性（completeness）、根据性（grounding，即抽取结果能否溯源到文档原文位置）与每页成本三个维度打分。
- **为什么重要**：这是一周前"文档 OCR 不会被前沿模型商品化"（2026-08-05）那篇立场文章的自然后续——上次是论证，这次是给出可复现的横向对比数据，把"专用解析器 vs 通用大模型"这场选型辩论从"我们认为"变成"这是实测结果"。三个评分维度也值得注意：completeness 和 grounding 分别对应此前反复强调的"别漏抽"和"空间定位/证据链"，成本维度则把选型拉回工程现实——不是精度越高越好，而是精度与每页成本的性价比曲线。虽然基准由 LlamaIndex 自建、立场与此前一致，但公开可复现的评测方法论本身对行业是净贡献。
- **分类**：RAG
- **关联 Topic**：[document-parsing](/topics/document-parsing)
- **来源**：https://www.llamaindex.ai/blog/introducing-extractbench

## Claude Compliance API 新增本地会话记录检索：Cowork / Claude Code 全程可审计

- **一句话总结**：Claude Enterprise 的 Compliance API 新增三个端点（`GET /v1/compliance/apps/sessions/local` 及其会话详情、消息记录），可检索运行在用户本机上的 Cowork 与 Claude Code 会话的完整记录与转录文本，目前为 beta，需现有 Compliance Access Key 及 `read:compliance_user_data` 权限范围。
- **为什么重要**：此前企业侧的推理层审计主要靠 Inference Hooks（2026-08-05 上线）在请求到达模型前做 allow/deny 裁决，但本地跑在员工电脑上的 Agent 会话本身"发生了什么"此前缺乏企业侧可见性；这次 Compliance API 把本地会话的完整转录也纳入可检索范围，补上了"事前拦截"之外"事后审计"这一环——两者合起来，企业侧对本地运行 Agent 的可观测性从"能不能拦"扩展到"发生过什么都能查"，是 Agent 治理工具链在企业合规维度的又一次补强。
- **分类**：其他（安全）
- **关联 Topic**：[agentic-safety](/topics/agentic-safety) ・ [claude-models](/topics/claude-models)
- **来源**：https://platform.claude.com/docs/en/release-notes/overview

## LangChain 用 NVIDIA Switchyard 实测：Agent 调用里只有 7% 真需要前沿模型

- **一句话总结**：LangChain 把自家 Deep Agents 评估集（145 个多步任务，平均每任务 6.3 次调用，覆盖客服、故障排查、工作流自动化）跑过 NVIDIA NeMo Switchyard（开源模型路由库），用"升级模式"在 Nemotron 3.5 Lightning（30B）与 Claude Opus 4.8 之间路由。结果：93% 的调用被路由到便宜的 Nemotron，只消耗 10.4% 的总花费；仅 7% 升级到 Opus，却吃掉 68.4% 的花费。整体路由方案跑出 80% 准确率、单次运行 $3.00（每完成任务 $0.026），相比 Opus 全程单跑的 86% 准确率、$11.45（每任务 $0.092），成本降 74%，准确率只掉 6 个百分点；Nemotron 单独全跑则是 77.7% 准确率、$0.72。文章同时给出路由是否划算的判断公式：判断模型（judge）成本 ÷（贵模型成本 − 便宜模型成本）< 卸载到便宜模型的工作占比，且判断模型开销本身占了路由总花费的 21.2%，两个模型价格越接近，路由越不划算。
- **为什么重要**：这是"多数 Agent 调用不需要前沿模型"这个直觉第一次被官方给出可复现的量化数据支撑，而不是停留在"SLM 该用在简单任务"的泛泛之谈——具体到 93%/7% 的调用分布、74% 的成本降幅、以及"判断模型成本 vs 价差"这个可执行的决策公式，把"该不该做模型路由"从经验判断变成了可以先算后做的工程决策。对正在设计多模型 Agent 架构的团队，这提供了一份可以直接套用的成本-准确率权衡框架。
- **分类**：Agent
- **关联 Topic**：[model-efficiency](/topics/model-efficiency) ・ [deep-agents](/topics/deep-agents)
- **来源**：https://www.langchain.com/blog/switchyard-agent-routing-benchmark

## LangChain：Agent 真正需要的不是更多工具，而是"自己的电脑"——以 monday.com Sidekick 为例

- **一句话总结**：LangChain 发文主张，Agent 能力的天花板不在于预置了多少工具，而在于能否拿到一个持久、隔离、可执行代码的运行环境；文章披露 monday.com 的 Sidekick 曾让单个 Agent 塞进 200+ 个预置工具，导致上下文被大量无关工具定义污染、模型判断力下降、成本上升，问题依然没解决。改用 LangSmith Sandboxes（硬件级虚拟化 microVM，非共享内核的容器）后，Sidekick 获得独立的文件系统、shell、包管理器、网络访问与跨会话持久状态，可以按需自己写代码、跑代码、看执行结果、动态调整，而不是被限定在预先想好的工具清单里。文章同时指出容器级隔离的现实风险：2025-09 的 Shai-Hulud npm 蠕虫通过 preinstall 脚本污染 500+ 个包，以及 CVE-2026-31431（一段 732 字节的 Python 脚本即可在主流 Linux 发行版上提权到 root）说明共享内核的容器不足以隔离"会执行不可信、模型生成代码"的 Agent。
- **为什么重要**：这是对"给 Agent 堆工具"这条路径天花板的一次具体案例反驳——200+ 工具反而让 Agent 变笨变贵，指向的架构结论是：能力应该来自"能自己动态找工具、执行、看结果、适应"的计算环境，而不是穷举式地预置工具。这与 Cloudflare computer（2026-08-06）把"存储层"和"执行后端"解耦的思路呼应，但这次多了一个明确的失败案例数据点（200+ 工具导致的上下文污染）和一个明确的安全动机（容器级隔离不足以防模型生成代码的供应链风险），让"Agent 需要一台真正的电脑"这个论点从架构直觉变成了有真实故障案例支撑的工程结论。
- **分类**：Agent
- **关联 Topic**：[agent-sandboxes](/topics/agent-sandboxes) ・ [deep-agents](/topics/deep-agents)
- **来源**：https://www.langchain.com/blog/give-your-ai-agent-its-own-computer

## IBM 开源 ALTK-Evolve：Agent 记忆压缩用"选择性投喂"把 token 成本砍掉 60%

- **一句话总结**：IBM Research 发布 ALTK-Evolve——Agent Lifecycle Toolkit 里的记忆组件，与 Sambanova 的 ACE（Agentic Context Engineering）思路同源：都从 Agent 执行轨迹里提炼"经验教训"、按支持次数（多少次独立任务验证了这条经验）沉淀成可复用的 guideline，且都反对"压缩总结"——保留逐条明细记录而非概括成笼统指令，避免"过度概括丢信息"。核心差异在投喂方式：ACE 每一步都把完整 playbook 整个塞进 prompt；ALTK-Evolve 把投喂做成可配置的——只给一小撮高支持度的核心准则打底，再按具体任务额外挑几条相关的。在 AppWorld 基准上，DeepSeek-V3.2 跑 168 个任务：ALTK-Evolve 达到 89.3% 任务目标完成率、每任务 26.3 万 token；ACE 是 80.4%、每任务 63.4 万 token——准确率更高，token 成本却只有 ACE 的约 40%。换成较弱的 gpt-oss-120b，两者准确率基本打平，但 ALTK-Evolve 只用了 ACE 约七分之一的 token（11.6 万 vs 77.7 万）。分难度看，困难任务上 ALTK-Evolve 优势更明显（gpt-oss-120b 上困难任务 31.8% vs ACE 的 23.8%），说明"精准挑对经验"比"把所有经验都塞进去"更关键，尤其是模型能力较弱、容易被过长上下文淹没时。
- **为什么重要**：这是 Agent 记忆/上下文工程领域一次具体的方法论优化——此前 ACE 提出的"别压缩总结，按条计数保留经验"已经是一次进步，但"每步都全量注入"仍然是显著的 token 成本；ALTK-Evolve 证明"保留全部明细 + 按需选择性投喂"可以两头兼得：既不损失 ACE 反对压缩换来的准确率收益，又能把 token 成本进一步砍掉六成到八成。对正在给 Agent 做长期记忆/经验复用系统的团队，这提供了一个具体可落地的优化方向：记忆存储保持精细粒度，但检索投喂环节要做选择性召回，而不是"记住的都发出去"。
- **分类**：Agent
- **关联 Topic**：[agent-memory](/topics/agent-memory) ・ [model-efficiency](/topics/model-efficiency)
- **来源**：https://huggingface.co/blog/ibm-research/altk-evolve-sldd
