## OpenAI and Broadcom Publish First Jalapeño Inference Chip Results: Beats NVIDIA Blackwell on Throughput and Latency

- **Summary**: OpenAI and Broadcom's custom inference chip Jalapeño (partnership announced 2025-10) published its first benchmark results. The chip is purpose-built for the inference phase — architected around bottlenecks in the prefill and communication stages, minimizing data movement and communication delay, with model state (including the KV cache used during generation) explicitly placeable and kept local. On SemiAnalysis's InferenceX benchmark across GPT-OSS 120B, DeepSeek R1 670B and Kimi K2.5 1T, Jalapeño delivered 1.5-1.9x higher peak performance per watt and 1.7-3.6x lower end-to-end latency than NVIDIA Blackwell systems (GB200/GB300); for highly interactive workloads, the gain reached 2.1-4.1x. OpenAI plans small-volume deployment into its own compute infrastructure by end of 2026, continuing to buy accelerators from NVIDIA and others, scaling up from 2027.
- **Why it matters**: Following Microsoft, Google and Amazon, another frontier-model vendor is now building custom inference silicon — and this is the first time one has published benchmarks directly against the industry-standard hardware, rather than staying at the "in development" announcement stage. Architecting specifically around inference-phase bottlenecks (rather than treating inference as a uniform compute workload) echoes this knowledge base's ongoing "utilization, not hardware scale, determines output" thread (Dharma AI's scheduling research) — the hardware layer and the scheduling layer are converging on the same goal of squeezing more useful output from every unit of compute (see [inference-serving](/en/topics/inference-serving)).

## LangSmith Engine Doubles Issue-Detection Accuracy: A Deep Agent That Auto-Diagnoses Production Agent Failures and Files Fix PRs

- **Summary**: LangSmith Engine (an in-platform Deep Agent that continuously scans production traces to find, group, diagnose and propose fixes for agent failures) announced a performance upgrade: it now scores over twice as well on the internal IssueBench benchmark, gained 25% on the public Terminal-Bench (which measures fix effectiveness), and has scanned 60M+ traces to identify 20,000+ issues to date. Each detected issue comes with an evidence chain (failing runs, an incident timeline, root-cause analysis), a ready-to-deploy fix PR (prompt or code change), formatted ground-truth examples for offline verification, and ongoing issue-specific regression monitoring. New features include self-hosted deployment, Slack/Linear integrations, and a cost-saving "reduced analysis" mode.
- **Why it matters**: A concrete productization of "agent production ops" evolving from manually combing through traces toward "a dedicated Deep Agent that auto-diagnoses and auto-fixes" — not just detecting problems (traditional observability already does that), but packaging root-cause analysis, fix generation and regression verification into one automated pipeline. It's essentially the "find the problem, propose the fix" pattern from AI code review, applied to an agent's own execution trajectory instead of human-written code (see [enterprise-ai-agents](/en/topics/enterprise-ai-agents)).

## LangChain Shares a Methodology for Building Agent Evaluation Environments and Tasks: A Spec-Generation + Spec2Task Pipeline

- **Summary**: LangChain published its internal methodology for building agent evaluation task sets — splitting "writing the task" into two stages: a human-reviewed spec-generation stage (a Markdown spec describing task input, execution environment and scoring rubric), then automated Spec2Task conversion where a coding agent turns the spec into an executable task. This split lets task creation run in parallel while concentrating human review at the cheapest, easiest-to-check stage. It introduces the "world spec" concept — project-level information shared across tasks in a dataset (data schemas, API specs, synthetic-data generation scripts, scoring methodology, domain patterns mined from production traces). Validation methods include running real agents against tasks to catch environment flaws and testing difficulty calibration across model tiers. The methodology has already been used to build internal benchmarks for GTM research, code review (based on real merged PRs), and trace mining.
- **Why it matters**: This is the first time the "real-task-derived benchmark" methodology has been systematically decomposed into the engineering process of "how you actually write the tasks," rather than just publishing results after the fact — separating "human-reviewed spec" from "agent-automated conversion" is a concrete path toward making benchmark construction itself an engineered, scalable process (see [agent-evaluation](/en/topics/agent-evaluation)).

## LangChain Releases OpenWiki's Self-Correcting Memory: Versioned Evidence per Claim, Auto-Flagged "Stale" When Code Changes

- **Summary**: LangChain shared the self-correcting memory design behind OpenWiki (a system that uses an agent to analyze a code repository and automatically generate and maintain wiki documentation). Core insight: "a memory system is only as good as its ability to forget" — as a codebase keeps evolving, previously accurate documentation goes stale, and traditional memory systems lack a mechanism to detect when the supporting evidence has changed, causing memory drift. OpenWiki represents every factual statement as a "claim + versioned evidence reference"; at runtime it compares the stored evidence version against current code, and when code changes, the dependent claim gets flagged as "stale" (rather than deleted outright); on the next wiki update, stale claims automatically surface for re-verification — refreshing the evidence version if it still holds, or updating both the claim and the docs if it's now invalid. Testing across 2,000 claims: the stale-claim rate dropped from 3.5% (baseline) to 0.5%, and hallucinated claims fell from 0.7% to 0%.
- **Why it matters**: A concrete solution to memory signal-to-noise management, a core engineering problem in memory infrastructure — prior memory discussion mostly focused on "how much to give and how to deliver it" (the ALTK-Evolve line); OpenWiki fills in the missing piece of "what happens when what you remembered goes stale," replacing the blunt "trust it all or delete it all" with "versioned evidence + stale flagging" (see [agent-memory](/en/topics/agent-memory)).
