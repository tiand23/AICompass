## ai-memory Open-Sources: A Long-Term Memory Layer for Coding Agents, With Seamless Cross-Vendor Handoff

- **Summary**: akitaonrails/ai-memory (+207 in a day, ~2.1k stars total, MIT) — a long-term memory system for coding agent CLIs, built around the scenario of "quit Claude Code mid-task, start OpenAI Codex in the same directory, continue without re-explaining the architecture." Rather than storing raw chat logs, it sanitizes session lifecycle events (prompts, tool calls, failures) and compiles them into a searchable Markdown wiki; at session end it generates a handoff summary with open questions and next steps, which the next agent receives before its first prompt as a "where you left off" briefing. Architecturally it's a single Rust binary managing one data directory (a git-versioned wiki as source of truth, immutable sanitized raw transcripts, a SQLite+FTS5 database, local embedding models, rolling logs); lifecycle hooks fire-and-forget events to a local HTTP server, which serializes writes to SQLite, compiles session pages, and serves retrieval via FTS5 full-text search, entity-match RRF, and optional vector search. It already implements hook adapters for Claude Code, Codex, Command Code, Devin, OpenCode, Cursor, and Kiro CLI — each agent's hook schema differs, but all POST observations to the same server, which is the key that makes cross-vendor handoff work. It also ships an MCP server (`memory_query`/`memory_write_page`/`memory_feedback` and other tools), a read-only web UI, and a "zero-LLM mode" that doesn't depend on any model call (falling back to FTS5 + declared entities + rule-based summaries).
- **Why it matters**: Prior memory-infrastructure discussion mostly focused on "how does the same agent/same vendor remember across sessions" — ai-memory extends the scope to "can memory travel with you when you switch to a different vendor's agent," a natural but so far rarely built next step now that using multiple coding-agent tools in parallel has become normal (holaOS reflected the same trend earlier): memory itself shouldn't be locked into a single vendor's harness. The "zero-LLM mode" design choice is also worth noting — the base retrieval/summarization capability doesn't depend on any model call at all, decoupling "having a memory system" from "being able to afford a large model," a pragmatic way to lower the adoption bar.

## IBM Research Follow-Up: Agent Memory Isn't "More Is Better" — It Should Be Calibrated by Model Tier

- **Summary**: IBM Research published a follow-up to ALTK-Evolve (the memory-distillation framework covered on 08-11), specifically probing how much memory different-sized models actually need — and the core finding overturns the "more memory is always better" intuition. The study covers 8 models (117B to 745B parameters) on AppWorld (585 multi-step tasks across simulated apps), measured via Task Goal Completion (TGC) and Scenario Goal Completion (SGC — full-pass reliability across task variants), and surfaces three distinct patterns: **capable, headroom-rich models** benefit from full-guideline injection — DeepSeek-V3.2 gained 9.5 percentage points in task completion with the full guideline set; **weaker/smaller models** instead do better with curated retrieval (a small core of high-support guidelines plus task-relevant picks) — gpt-oss-120b gained 16.1 points over baseline with curated retrieval while spending only 5% more tokens; **already-saturated models** show no gain at all — GLM-5 improved by 0.0 percentage points under either delivery mode, suggesting a capability ceiling or a guideline-relevance bottleneck. On cost, curated retrieval buys better accuracy for minimal extra tokens, while full injection adds 51%-78% token cost (reliable prompt caching can partly offset production cost).
- **Why it matters**: This reframes "agent memory optimization" from "pile more on" to "calibrate the dose" — how much memory to give depends on the model's tier, not on maximizing information volume. It's an important extension of the 08-11 ALTK-Evolve finding ("selective delivery saves tokens without losing accuracy"): that earlier result proved curated retrieval works as a path; this one reveals that "curated retrieval works" is itself not a universal truth but a tier-dependent phenomenon — capable models need "enough information," weak models need "precisely enough information," and saturated models gain nothing from either. For teams designing memory systems, this means "one memory-delivery strategy for everyone" may itself be the wrong assumption — tuning needs to happen per target-model capability tier.

## Sentence Transformers v6.0 Natively Supports Multi-Vector (Late-Interaction) Embeddings: ColBERT-Style Retrieval Enters the Mainstream Library

- **Summary**: Sentence Transformers v6.0 adds `MultiVectorEncoder`, natively supporting ColBERT-style multi-vector (late-interaction) embedding models — unlike dense embeddings that compress an entire document into a single vector, multi-vector models keep one vector per token (a 9-token document becomes a 9×128 matrix rather than a single 1×128 vector), deferring "interaction" to scoring time, combining a bi-encoder's offline-indexing capability with a cross-encoder's fine-grained query-document comparison. Scoring uses the MaxSim operator: for each query token, find the document token with the highest similarity and sum across query tokens — a soft alignment where "each query word points to the document word that best explains it," able to catch matches like "live" and "inhabit" that share zero characters but are semantically related (similarity 0.94), without losing exact matches. The new library natively supports arbitrary PyLate and Stanford-NLP ColBERT checkpoints, plus the ColPali vision-document model, offering asymmetric `encode_query()`/`encode_document()` interfaces across text/image/audio/video modalities. Benchmark data: at matched model scale, the multi-vector version (LateOn, 0.6868 average NDCG@10) beats the corresponding dense version (DenseOn, 0.6764) on 9 of 13 NanoBEIR datasets; but storage cost is far higher — encoding 4,874 Natural Questions passages, dense (MiniLM) needs only 7.5MB, while multi-vector (128-dim) needs 311.5MB raw (about 92MB after PLAID-index compression); token pooling (pool_factor=2) can halve the vector count with under 1% accuracy loss. Native indexing is already supported by Qdrant/Weaviate/Vespa/LightOn fast-plaid, with fast-plaid achieving ~11ms query latency approximating PLAID indexing on the 4,874-document set.
- **Why it matters**: This is the first time a previously niche technical path — ColBERT-style multi-vector retrieval — on the "retrieval accuracy vs. storage cost" trade-off curve gets formally adopted by a mainstream library. Multi-vector retrieval was mostly confined to papers and specialized libraries (like PyLate) before; native Sentence Transformers support means it's now a regular option in production-grade RAG/retrieval stack selection, not an experimental setup you have to assemble yourself. Beating same-scale dense models on 9 of 13 datasets gives reproducible, controlled evidence for the long-cited but rarely uniformly-verified claim that "dense vectors lose information through compression"; the order-of-magnitude storage cost also means this isn't a free lunch — it needs to be weighed against your own recall requirements and storage budget rather than adopted by default.

## LangSmith Launches "Tuned Evaluators": Specialized Small Models Judge Agents More Accurately Than Frontier Models, at 82% Lower Cost

- **Summary**: LangSmith released Tuned Evaluators — a managed evaluation service that turns "automatically attach useful signal to production traces" from "build your own evaluator" into "just attach and go": LangChain end-to-end maintains a pretrained, version-managed judge model, handling prompt engineering, model selection, credential management and infrastructure, so teams just attach it to a tracing project. The first evaluator shipped is Perceived Error detection — identifying conversations where "the agent made a mistake, misunderstood the request, or steered the interaction off course," drawing on both explicit signals (user corrections, refusals) and implicit inference (self-contradictory replies, admitted mistakes, unresolved outcomes). The model gets its specialized capability through post-training on labeled conversational agent traces, and in testing "outperforms all frontier models" on judgment accuracy while cutting cost by 82% — up to 98% for some customer workloads depending on conversation composition. Eligibility: threads need at least two rounds of human-AI message pairs plus a configured idle period; evaluation completes within 12 hours once eligible; currently available only on Plus and Cloud Enterprise US; billing applies only to successful evaluation runs, with skipped or failed evaluations free.
- **Why it matters**: This is a productized instance of "replace frontier models with specialized small models for LLM-as-judge" landing in the specific domain of evaluation — this cost-reduction idea previously showed up mostly as research findings or DIY solutions (like the 08-11 model-routing results); here an evaluation-toolchain vendor itself turns it into an out-of-the-box managed service, with no need for users to train or maintain a judge model themselves. "More accurate than frontier models, and cheaper" is itself worth noting: a specialized post-trained model outperforming general frontier models' judgment on a narrow task (detecting whether a conversation went wrong) is further empirical evidence for the efficiency philosophy that "vertical scenarios don't need frontier intelligence" — extending, in this case, to the evaluation tooling itself. This also continues the knowledge base's recurring "vertical benchmark built by the domain's own participants" pattern — this time it's the evaluation tool itself, not an evaluation benchmark, being specialized.
