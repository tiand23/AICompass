## OpenAI Previews Private Safety Processing: Cross-Interaction Abuse Detection Without Breaking Zero Data Retention

- **Summary**: OpenAI announced it is testing Private Safety Processing with early customers — a safety monitoring system that identifies misuse patterns across multiple related interactions while preserving its Zero Data Retention (ZDR) commitment. The motivation is a limitation of existing ZDR-compatible safety systems: they can only evaluate each interaction in isolation, while as models take on longer, more autonomous tasks, some serious risks (like a long-horizon task an agent gets manipulated into carrying out maliciously) only become visible across multiple turns. The new system sends OpenAI only a narrowly defined "safety signal" (e.g. a suspected-misuse flag), never exposing the underlying prompts or responses; customer data can either stay on customer-controlled infrastructure or be stored by OpenAI with encryption keys the customer controls. Currently available for testing to eligible enterprise and API customers, not consumer ChatGPT subscribers; a broader rollout and technical white paper are planned for September.
- **Why it matters**: This is a concrete architectural compromise between "privacy protection" and "safety monitoring" — two goals previously seen as trading off against each other. Where ZDR's cost has typically been zero visibility into interaction content for safety teams, Private Safety Processing tries to show that "retaining no raw content" and "detecting cross-interaction misuse patterns" can coexist, by dropping granularity from "content" to a "narrow signal." For enterprise customers handing agents long-horizon autonomous tasks, this kind of cross-session behavioral monitoring is essentially another instance of this knowledge base's ongoing "EDR for Agents" narrative extending from passive runtime detection (like Uber ADR) toward a hosted capability offered by the model vendor itself at inference time; reporting also frames it as a competitive differentiation against Anthropic's existing compliance log-retention requirements.

## Claude Platform's Agent Skills API Reaches GA; Managed Agents Adds Web-Tool Domain Allow/Block Lists

- **Summary**: The Claude Platform release notes announced a batch of APIs reaching general availability (no beta header required): ① **Agent Skills and the Skills API** (`/v1/skills`) are now GA, including Messages API requests that load Skills via the `container` parameter; ② the Files API (`/v1/files`) is now GA, with file expiration and pagination; ③ the Admin API's user-management endpoints for Claude Enterprise organizations (members, invites, groups, custom roles) are now GA. The same batch adds a new Managed Agents security control: an agent's `web_search`/`web_fetch` tools can now be scoped with `allowed_domains` or `blocked_domains`, with `web_fetch` also supporting `max_content_tokens` to cap fetched-content length and `web_search` supporting `user_location`. All changes are backward-compatible — requests still sending the old beta headers keep working in the previous format.
- **Why it matters**: The Skills API's move from beta to formal GA marks an official, production-grade API commitment for the rapidly expanding Skill ecosystem this knowledge base has tracked since October 2025 (its "ecosystem heat" ranking already lists a dozen-plus high-star third-party repos) — third-party tools and enterprise integrations no longer need to worry about beta headers shifting underneath them. Managed Agents' domain allow/block lists are a concrete instance of the least-privilege principle applied to hosted agents' network access — where this principle previously showed up mostly at the tool-permission and credential-injection layer, control granularity now reaches down to "which specific domains can an agent reach over the network," another step in the ongoing refinement of hosted-agent security configuration options.

## LiquidAI Releases Quantization-Aware Distillation (QAD) Q4_0 Checkpoints: Edge Models Recover 96%-97% of BF16 Performance

- **Summary**: LiquidAI's HuggingFace blog introduces Quantization-Aware Distillation (QAD) and releases corresponding QAD Q4_0 checkpoints for four models in the LFM2.5 line (230M, 350M, 1.2B-Instruct, 2.6B). Unlike post-training quantization (PTQ), which compresses a model after training is complete, QAD integrates quantization directly into the distillation process — a high-precision teacher model guides training of the quantized student, so the model learns to preserve capability under quantization constraints from the start, rather than being trained first and compressed afterward. Across benchmarks including GPQA Diamond, MMLU-Pro, IFEval, GSM8K and AIME25, the four models' QAD Q4_0 checkpoints recovered 97.1%, 96.5%, 97.4% and 96.6% of BF16 full-precision performance respectively; compared to the higher-bit quantization needed to reach equivalent quality (Q5_K_M for smaller models, Q4_K_M for larger ones), QAD Q4_0 achieves 4-33% higher decode throughput (smaller models) and 3-14% higher throughput (larger models). Target edge hardware includes MacBook Pro, NucBox EVO-X2, Samsung Galaxy S26 Ultra and Raspberry Pi 5; the models are released under the LFM1.0 license.
- **Why it matters**: This is a concrete methodological fusion on the low-bit-quantization efficiency route — turning quantization from an after-the-fact compression step into a training-time objective, using distillation to offset the accuracy loss quantization would otherwise cause, merging two previously separate technical paths (quantization and knowledge distillation). Retaining 96%+ accuracy while also gaining double-digit throughput is especially meaningful for edge deployment, where 4-bit precision is often mandatory and teams previously had to make a harsher trade-off between accuracy and speed; QAD offers a concrete path to getting both, and is another step in Liquid AI's ongoing edge-model efficiency product line (see [model-efficiency](/en/topics/model-efficiency)).
- **Category**: Models
- **Related Topic**: [model-efficiency](/en/topics/model-efficiency)
- **Source**: https://huggingface.co/blog/LiquidAI/qad

## Claude API Adds a Browser-Use Tool, Computer-Use Tool Reaches GA, Managed Sandboxes Gain Memory-Store Attachment (backfilled)

- **Summary**: The Claude Platform shipped three agent-tooling updates in the same batch: ① a **browser-use tool** (`browser_toolset_20260801`) — unlike the computer-use tool, which controls an entire desktop, it operates only inside a browser viewport, reading the page's accessibility tree/elements/forms/tabs directly, with element grounding, form input, tab management, download reporting and optional file upload; ② the **computer-use tool** (`computer_toolset_20260801`) reaches formal GA, no beta header required, adding batched actions, zoom on by default, and per-member configuration; ③ Managed Agents sessions running in a self-hosted sandbox can now attach **memory stores** — an SDK worker downloads the store into the sandbox at session start and syncs the agent's changes back. All three are available on Fable 5, Mythos 5, Opus 5, Sonnet 5 and Opus 4.8.
- **Why it matters**: Splitting "computer operation" into "full desktop control" and "in-browser action" is a concrete instance of least-privilege in tool design — most tasks only need browser access, and full desktop control is an unnecessary attack surface; reading the accessibility tree instead of screenshot-and-click also frees browser automation from depending on vision-model precision. Letting memory stores attach directly to sandbox sessions pushes agent memory capability down into the hosted execution environment itself (see [agent-memory](/en/topics/agent-memory)).
