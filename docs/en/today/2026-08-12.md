## needle 2 Arrives: A 14MB Single-File Foundation Model Built for Phones, Wearables and Robots

- **Summary**: cactus-compute/needle (+315 in a day, 4.6k stars total, MIT) — an extremely compact foundation model built for resource-constrained environments like phones, wearables, smart-home devices, and robots: the entire model is a single 14MB binary, running in roughly 28MB of RAM during inference (a 256-token sliding window with tool definitions pinned as KV sinks). The architecture replaces standard feed-forward networks with Hadamard MLPs, paired with grouped query attention (GQA), an Engram key-value memory using hashed n-gram tables, multi-lane hyper-connections, and RMS normalization with sandwich gating — compressed to this size via Cactus Quants' CQ2-bit quantization; the design is documented in a paper on arXiv (2607.18363). Functionally it focuses on tool calling (gated by calibrated confidence scores), tool retrieval for large catalogs (ranking and selecting the top five per turn), schema-based structured extraction via Pydantic models, and grammar-constrained decoding to guarantee valid JSON. Official claims: it's 5-70x smaller than comparable small models like FunctionGemma 270M, LFM2.5 230M and Apple FM (and running at 2-bit versus their f16), trading wins with them on benchmarks.
- **Why it matters**: A new low-water mark on the size axis of the SLM/edge-model line — a 14MB single file running in 28MB of RAM turns "a foundation model that fits on a watch or a robot" from a concept into something you can actually download and run. More notable than the parameter count is its functional focus: rather than chasing general conversational quality, it specializes in the two most core agentic actions — tool calling and structured extraction — with native confidence gating and large-tool-catalog retrieval built in. This treats "agents on resource-constrained devices" as its own product category to design for, rather than just shrinking a large model.
- **Category**: Models
- **Related Topic**: [model-efficiency](/en/topics/model-efficiency)
- **Source**: https://github.com/cactus-compute/needle

## LlamaIndex: LLM OCR Errors Aren't Getting Rarer — They're Getting Quieter

- **Summary**: LlamaIndex published a post arguing that LLM-driven OCR fails in a fundamentally different way from traditional OCR — engines like Tesseract fail into "visibly broken garbage," while LLMs fail into fluent, plausible-looking text that masks missing or incorrect content. The piece breaks down three mainstream architectures (OCR-then-LLM correction with no pixel access, native VLM transcription, and agentic segmentation-based orchestration), each failing in its own way. The core mechanism: when visual evidence is ambiguous, models favor "what's most probable as text" over "what's best supported by the image" — high-entropy strings like account numbers and part numbers are especially vulnerable, since the language prior is weakest exactly where it's needed most. The article also argues existing metrics fail: character/word error rate average across a page, so a page reporting "99% character accuracy" can still be worthless if the 1% wrong represents a total or an identifier. Its conclusion: production systems need architectural controls — segmentation, routing to specialized models, validation loops, and citations linking output back to source pixels — that raw models can't provide on their own.
- **Why it matters**: An important methodological addition to the document-parsing thread — the 08-05 "OCR won't be commoditized" piece and the 08-11 ExtractBench release respectively argued "specialized engines are stronger" and supplied reproducible comparison data; this post fills in the deeper mechanism: why LLM OCR errors are specifically dangerous — not because there are more of them, but because they're more disguised, more plausible-looking. The insight that "page-averaged metrics mask critical-field errors" is a directly actionable methodology fix for any team using CER/WER-style metrics for acceptance testing — accuracy should be measured per field type (especially high-entropy fields), not as a single page-average score.
- **Category**: RAG
- **Related Topic**: [document-parsing](/en/topics/document-parsing)
- **Source**: https://www.llamaindex.ai/blog/llm-ocr

## Microsoft Azure Proposes a "Three-Speed" Model for Agent Cost Optimization: Runtime Routing, Workflow Iteration and Continuous Governance, Each at Its Own Pace

- **Summary**: Azure published "The Economics of Agent Optimization," citing a Microsoft-commissioned IDC survey of 4,000+ business leaders (71% plan to increase AI budgets) and the fact that 100,000+ organizations are already building on Microsoft Foundry, to argue that enterprise agent cost management should run at three different speeds simultaneously: **runtime optimization** (routing each request to a right-sized model in real time), **workflow optimization** (improving agent efficiency over days/weeks through testing), and **continuous governance** (enforcing spending caps that don't get relaxed on demand). The piece offers four self-check questions (Do you have cost visibility by model/agent/workflow? Are requests over-provisioned to unnecessarily capable models? Is agent efficiency improving over time? Can you enforce spending limits during usage spikes?) and names concrete Microsoft Foundry capabilities: a model router (cost-optimized request routing), prompt/semantic caching (context reuse), an agent optimizer (testing configurations), and Azure API Management's AI Gateway (token rate limits). Its core argument: shift from "buying intelligence" (one-off pilots) to "managing it" (bounded, accountable spend across the AI lifecycle).
- **Why it matters**: This piece organizes agent cost-reduction tactics that were previously scattered (model routing, prompt caching, evaluation-driven efficiency iteration, hard spending caps) into a single "three speeds" governance framework, rather than listing them as isolated tricks — the layering itself is worth borrowing: runtime-level optimization is nearly free but limited in impact, workflow-level needs ongoing investment for bigger returns, and governance-level creates no efficiency gains but backstops risk exposure — all three need to run together, not as an either-or choice. It's also a natural enterprise-governance extension of LangChain's Switchyard model-routing benchmark (08-11) — putting the engineering question of "should we route models" inside a more complete organizational cost-management framework.

## Liquid AI Releases LFM2.5-VL-3B: An Edge Vision-Language Model Matching Larger Models on Several Capabilities

- **Summary**: Liquid AI released LFM2.5-VL-3B, the LFM2.5 series' first vision-language model — a SigLIP2 400M NaFlex vision encoder paired with a 2.6B-parameter text backbone, pre-trained on roughly 34 trillion tokens (4x more vision data than the prior generation), with the tokenizer expanded to a 128K vocabulary for non-Latin scripts. Across 34 evaluated tasks it scored a 69.4% average normalized performance: document/OCR (DocVQA 91.1%, OCRBench v1 84.2%), grounding (RefCOCO-avg 87.9%), UI understanding (ScreenSpot-v2 Desktop 78.7% / Mobile 81.2% / Web 82.2%), multi-image (BLINK 61.5%), and tool use (ToolSandbox 59.5%) — all beating comparable 3B-class models, with some scores matching larger 4B-class models. Edge inference: 228 tokens/sec on an M5 Max, 116 tokens/sec on a Ryzen AI Max+, using roughly 3GB of memory; 20 tokens/sec on a Galaxy S26 Ultra; roughly 11,000 tokens/sec GPU throughput at high concurrency, about double comparable 4B-class models. Supports llama.cpp, MLX, vLLM, SGLang and ONNX.
- **Why it matters**: A natural extension of the LFM2.5 line from text-only (LFM2.5-2.6B) into multimodal — expanding the "core reasoning engine for local agents" role from text into screen/UI understanding, multi-image input and visual grounding. The ScreenSpot and tool-use scores specifically matter because they map directly to the concrete scenario of "an edge agent needs to understand a screen before it can act on it," not generic image Q&A. Shrinking further while keeping pace with larger models reinforces this knowledge base's recurring finding that the efficiency route doesn't have to trade away capability (see [model-efficiency](/en/topics/model-efficiency)).
