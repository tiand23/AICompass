## Cloudflare Open-Sources computer: A Programmable "Computer" for Agents

- **Summary**: Cloudflare open-sourced computer (+891 stars in a day, 2,900 total) — a virtual filesystem living inside a Durable Object (state stored in SQLite), paired with three pluggable execution backends: Container (projects state as a real FUSE mount with full Linux userland and network access), Isolate Shell (runs just-bash in a Dynamic Worker, reaching the workspace via Workers RPC), and Isolate JavaScript (executes ES modules in a fresh Dynamic Worker). A single entry point, `workspace.runtime.exec()`, unifies them; a workspace can also run without any backend attached. Explicitly marked "preview only, not suitable for production yet."
- **Why it matters**: A hyperscaler's own take on the "agent-sandbox-as-a-service" idea pioneered by E2B/Daytona — and it decouples "filesystem state" from "execution backend" into two independent layers: the same workspace state can switch between a real container, an isolated shell, or a pure JS sandbox on demand, rather than being locked to one isolation strength. The architectural lesson: an agent execution environment's storage layer and isolation layer should be two independently swappable components, not bundled together the way most sandbox products do.
- **Category**: Agent
- **Related Topic**: [agent-sandboxes](/en/topics/agent-sandboxes)
- **Source**: https://github.com/cloudflare/computer

## loopx Arrives: A "State Kernel" for Long-Running Agent Teams

- **Summary**: huangruiteng/loopx (+326 stars in a day, 2.1k total) — doesn't replace the agent runtime itself; instead it adds a local control plane on top of any agent (Codex, Claude Code, Cursor, custom runners): an "agent-native Kanban" with Durable Goals that survive across many turns and sessions, claimable/handoff-able Executable Todos, Quota-Aware Scheduling (proceed / ask a human / wait / stop based on budget), an evidence log preserving decisions and validation, and typed Verifiable Handoffs between peer agents.
- **Why it matters**: It hits a real gap in long-horizon multi-agent collaboration precisely — chat interfaces are structurally unsuited to carrying state that drifts (goals shift, ownership changes hands, evidence goes stale, costs pile up silently across sessions). loopx isn't another agent framework; it's an agent-agnostic external state-management layer. This "state kernel sitting outside the runtime" design choice is worth comparing to AIDD's Staging Area + evidence-chain approach — both are, at core, adding an auditable persistent state layer on top of autonomous execution.
- **Category**: Agent
- **Related Topic**: [deep-agents](/en/topics/deep-agents)
- **Source**: https://github.com/huangruiteng/loopx

## LangChain Publishes a Post Clarifying Deep Agents vs LangChain vs LangGraph

- **Summary**: LangChain's official positioning of the three: Deep Agents is an "opinionated" agent harness with best practices out of the box (built-in filesystem backends, subagents, skills, memory management); LangChain is a minimal framework for "an LLM, running in a loop, calling tools", customized via middleware hooks; LangGraph is a graph-based agent runtime that lets you encode domain knowledge directly into the graph topology rather than relying entirely on model judgment, maximizing determinism. All three are composable and deployable via LangSmith — at core, three points on the same tech stack's "agency (flexibility) ↔ determinism (reliability)" spectrum.
- **Why it matters**: LangChain's first systematic answer to the frequent question "which of your products should I use" — with concrete selection criteria: pick Deep Agents for complex, long-running tasks that need out-of-the-box context management; pick LangChain when you need fine-grained control over exactly which tools and context reach the model at each step; pick LangGraph when the workflow doesn't fit a standard loop and needs a mix of deterministic and agentic steps. For teams already running enterprise workflows on LangGraph, this positioning also indirectly answers "when should I tighten control into a graph, versus hand judgment to an autonomous agent" — a real architectural decision.

## OpenAI Confirms Astra's Internal Math Results: A 27-Year-Old Open Problem Formally Proved

- **Summary**: OpenAI officially confirmed the codename of its next flagship model, **Astra**, alongside a 249-page manuscript: an internal build of Astra resolved 10 open problems — each unsolved for over a decade — across 5+ mathematical fields including group theory, high-dimensional geometry, quantum complexity, lattice cryptography and extremal combinatorics, producing machine-verifiable Lean 4 formal proofs for all of them, with a GitHub "sorry" count of zero (no unverified proof steps remain). Total compute cost was roughly $2,000. The headline result is the **first explicit construction of a non-sofic group** — a problem posed in 1999 that no human mathematician had solved in 27 years. The manuscript and proof certificates are open-sourced under Apache 2.0. Astra itself has no announced release date or pricing, and must clear US government security review before it can be made available.
- **Why it matters**: This marks a step-change in "AI doing math" — from "clearing competition-style benchmarks" to "producing formal proofs of open problems humans hadn't solved in 27 years." Machine-verifiable proof (Lean 4, zero "sorry" count) means the result doesn't depend on trusting the model's output — it can be independently checked, which is far more solid evidence of capability than a leaderboard score. For model selection and technology-trend judgment, this signals frontier reasoning capability genuinely reaching the edge of human-expert ability — and the fact that release itself now requires government security review is a signal that capability has reached a point warranting national-level oversight.

## Claude Code Ships Self-Hosted Execution Environments in Public Beta: Sessions Can Run Directly Inside a Company's Own Network

- **Summary**: Anthropic launched Self-Hosted Environments for Claude Code in public beta: organizations on Team/Enterprise plans can run sessions on their own infrastructure instead of Anthropic-hosted servers — sessions started from the web, mobile, desktop, terminal, or a scheduled routine are all routed into the organization's own network, next to its internal services, toolchains and security controls. Architecturally, long-lived runner processes pick up sessions and spawn individual Claude Code processes, in either a fixed-count mode or an on-demand mode (an orchestrator dynamically spins runners up and down as sessions queue); each session runs in an isolated checkout to prevent cross-developer interference. Repository checkouts, build artifacts and generated files stay on customer infrastructure — but conversation content and prompts still go to Anthropic for inference, and session transcripts are stored remotely to support cross-surface continuity — meaning "execution is local," not "everything is local." Off by default; requires organizations to build and maintain their own runner images and orchestration. Not available to Zero Data Residency (ZDR) customers.
- **Why it matters**: This is the same "decouple storage from execution" idea Cloudflare's computer demonstrated the same day, landing inside a leading vendor's own flagship coding agent — Claude Code's execution environment (the runner) is split from the cloud inference service (the model itself), with the former able to move inside a customer's network while the latter stays with Anthropic. This maps precisely onto a common enterprise compliance line: "source code can't leave the intranet, but sending prompts/conversation content to a vendor for inference is acceptable" — a more finely-grained third option than the usual "fully managed or fully self-built" binary. Anthropic's candid note that organizations must still build and maintain their own runner images and orchestration is also a useful, realistic correction to the over-optimistic assumption that "self-hosted = zero-cost compliance."
