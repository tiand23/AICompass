## LlamaIndex Releases ExtractBench: An Extraction Benchmark Across 370 Real Enterprise Documents and 14 Systems

- **Summary**: LlamaIndex introduced ExtractBench — an open benchmark testing 14 extraction systems against 370 real enterprise documents, scored across three dimensions: completeness, grounding (whether an extracted result can be traced back to its exact location in the source document), and cost per page.
- **Why it matters**: This is the natural follow-up to last week's ("document OCR won't be commoditized by frontier models," 2026-08-05) position piece — that one was an argument, this one supplies reproducible head-to-head data, turning the "specialized parser vs general frontier model" selection debate from "we believe" into "here's the measured result." The three scoring dimensions are worth noting too: completeness and grounding map directly to the previously emphasized "don't miss extractions" and "spatial grounding/evidence chain," while the cost dimension pulls selection back to engineering reality — it's not "higher precision always wins," but a precision-vs-cost-per-page curve. The benchmark is LlamaIndex's own (same stance as before), but a publicly reproducible evaluation methodology is a net contribution to the field regardless.

- **Related Topic**: [document-parsing](/en/topics/document-parsing)

## Claude Compliance API Adds Local Session Transcript Retrieval: Cowork/Claude Code Now Fully Auditable

- **Summary**: Claude Enterprise's Compliance API gained three new endpoints (`GET /v1/compliance/apps/sessions/local` plus per-session detail and message-transcript retrieval) that can retrieve the full record and transcript of Cowork and Claude Code sessions running on a user's own machine — currently in beta, requiring an existing Compliance Access Key with the `read:compliance_user_data` scope.
- **Why it matters**: Enterprise-side inference auditing has so far relied mainly on Inference Hooks (shipped 2026-08-05), which issue an allow/deny verdict before a request reaches the model — but organizations previously had no visibility into what actually happened inside agent sessions running locally on an employee's machine. The Compliance API now makes those local session transcripts retrievable too, filling in the "after-the-fact audit" half that pre-inference blocking alone doesn't cover. Together, the two give enterprises observability over locally-run agents that spans both "can we block it" and "can we see everything that happened" — another reinforcement of the agent-governance toolchain on the enterprise-compliance axis.

## LangChain Benchmarks NVIDIA Switchyard: Only 7% of Agent Calls Actually Need a Frontier Model

- **Summary**: LangChain ran its own Deep Agents evaluation suite (145 multi-step tasks averaging 6.3 calls each, spanning customer support, incident investigation, and workflow automation) through NVIDIA NeMo Switchyard, an open-source model routing library, in "escalation mode" between Nemotron 3.5 Lightning (30B) and Claude Opus 4.8. Result: 93% of calls were routed to the cheaper Nemotron, consuming just 10.4% of total spend; only 7% escalated to Opus, which consumed 68.4% of spend. The routed setup hit 80% accuracy at $3.00 per run ($0.026 per completed task), versus Opus alone at 86% accuracy for $11.45 per run ($0.092 per task) — a 74% cost cut for a 6-point accuracy loss. Nemotron alone scored 77.7% accuracy at $0.72 per run. The article also gives a formula for whether routing is worth it: judge-model cost ÷ (expensive-model cost − cheap-model cost) < the share of work offloaded to the cheap model — with the judge itself accounting for 21.2% of routed spend, meaning routing pays off less as the two models' prices converge.
- **Why it matters**: This is the first time the intuition that "most agent calls don't need a frontier model" has been backed by official, reproducible quantitative data rather than a vague "use SLMs for simple tasks" heuristic — concrete numbers (93%/7% call distribution, 74% cost reduction) plus an executable decision formula (judge cost vs. price gap) turn "should we route models" from a judgment call into something you can calculate before building. For teams designing multi-model agent architectures, this is a directly reusable cost-accuracy tradeoff framework.

## LangChain: What Agents Actually Need Isn't More Tools — It's Their Own Computer, as monday.com's Sidekick Shows

- **Summary**: LangChain argues that an agent's capability ceiling isn't set by how many tools it's pre-loaded with, but by whether it has a persistent, isolated environment for executing code. The article reveals that monday.com's Sidekick assistant once crammed 200+ pre-defined tools into a single agent, polluting its context with irrelevant tool definitions, degrading judgment, and driving up cost — without solving the underlying problem. Switching to LangSmith Sandboxes (hardware-virtualized microVMs, not kernel-sharing containers) gave Sidekick its own filesystem, shell, package manager, network access and cross-session persistent state, letting it write and run code, inspect results, and adapt dynamically rather than being confined to a pre-built tool list. The article also flags real risks of container-level isolation: the September 2025 Shai-Hulud npm worm, which compromised 500+ packages via preinstall scripts, and CVE-2026-31431 (a 732-byte Python script that roots every major Linux distribution) — evidence that kernel-sharing containers aren't isolation enough for agents executing untrusted, model-generated code.
- **Why it matters**: This is a concrete counter-example to the ceiling of "just give the agent more tools" — 200+ tools made the agent dumber and more expensive, pointing to an architectural conclusion: capability should come from a computing environment that can dynamically find, run, inspect and adapt, not an exhaustively pre-built tool catalog. It echoes Cloudflare's computer (2026-08-06), which decoupled the "storage layer" from the "execution backend," but adds a concrete failure data point (context pollution from 200+ tools) and a concrete security motivation (container isolation isn't enough against model-generated-code supply-chain risk) — turning "agents need a real computer" from architectural intuition into an engineering conclusion backed by a real incident.

- **Source**: https://www.langchain.com/blog/give-your-ai-agent-its-own-computer

## IBM Open-Sources ALTK-Evolve: Cutting Agent Memory Token Cost 60% With Selective Delivery

- **Summary**: IBM Research released ALTK-Evolve, a memory component of its Agent Lifecycle Toolkit, sharing its core premise with Sambanova's ACE (Agentic Context Engineering): both distill "lessons" from execution trajectories and consolidate them into reusable guidelines tracked by support count (how many independent episodes validated each rule), and both reject compression — keeping itemized detail rather than summarizing into generic instructions, which loses information. The key difference is delivery: ACE injects the complete playbook at every step; ALTK-Evolve makes delivery configurable — a small fixed core of high-support guidelines, extended per task with a handful selected for that specific task. On the AppWorld benchmark, DeepSeek-V3.2 running 168 tasks: ALTK-Evolve hit 89.3% task-goal completion at 263K tokens/task, versus ACE's 80.4% at 634K tokens/task — better accuracy at roughly 40% of ACE's token cost. On the weaker gpt-oss-120b, accuracy was roughly tied, but ALTK-Evolve used about one-seventh of ACE's tokens (116K vs. 777K). Broken down by difficulty, ALTK-Evolve's advantage grows on hard tasks (31.8% vs. ACE's 23.8% on gpt-oss-120b), suggesting that picking the right lessons matters more than having all of them available — especially on weaker models, where an overly long context overwhelms capability.
- **Why it matters**: A concrete methodological refinement in agent memory/context engineering — ACE's earlier insight ("don't compress, keep itemized counts") was already a step forward, but injecting the full playbook at every step still carries a significant token cost. ALTK-Evolve shows that "keep full detail in storage, deliver selectively" gets both: it doesn't sacrifice the accuracy gains ACE earns by avoiding compression, while cutting token cost by a further 60-85%. For teams building long-term memory/experience-reuse systems for agents, this offers a concrete direction: keep the memory store fine-grained, but make retrieval-time delivery selective rather than dumping everything remembered into every prompt.
- **Category**: Agent
- **Related Topic**: [agent-memory](/en/topics/agent-memory) ・ [model-efficiency](/en/topics/model-efficiency)
- **Source**: https://huggingface.co/blog/ibm-research/altk-evolve-sldd
